# paged KV, stages 2 and 3: the pool allocates pages, and serve plans by pages

- Date: 2026-10-17. Branch: feat/paged-kv-pool on main 69adfa2 (after #64 stages 0+1 and #68).
  Two commits: stage 2 (the pool allocates pages), stage 3 (serve policy). Status: open, not merged.
- Design: specs/r11-paged-kv.md §2.3 (allocator, policy), §2.4 (neighbours), §3.1 (tests), §4 stages 2 and 3;
  forum "r11: paged KV design".

## Why
A pool on main is `slots x ctx` reserved rows: Qwen2.5-7B f16 at the default 32768 context gets 2 slots on a
12 GB card (1.75 GiB each) whether a request holds 300 tokens or 30k, and `--kv q8` gets 5. Stages 0+1 (#64)
put every cache kernel behind a page table (null = the old addresses) at no measured cost; this PR makes the
pool use it: a slot holds pages only for the positions it has, `--ctx` becomes a per-slot cap, and the memory
left after the weights is a page budget shared by as many requests as fit.

## What changed
Stage 2 (`pages.rs`, `slots.rs`, `kvio.rs`, `lm.rs`, engine hooks):
- `PageMap` (host): per-slot page lists in position order, a LIFO free list (`AXON_PAGE_SHUFFLE=seed`:
  seeded random pops), a retire list flushed once no work in flight can read it, and the invariants of §2.3
  (`check`: every page in exactly one place, no slot past its cap). `ensure` is all-or-nothing.
- `CudaPool` is a paged cache: rows = (pages + 1) x 64 (the extra page is a sink: every table entry a slot
  doesn't hold points there, so a stray write lands nowhere that matters), a device table `slots x cap` at a
  fixed address (graphs hold it; contents change, uploaded synchronously before the work that reads them).
  `reserve(slot, hi)` takes pages for positions `..hi` (Ok(0) or the pages short, nothing taken),
  `release(slot, lo)` frees the tail. `feed_slot` and `step_rows` reserve their own positions (a step past
  the pages: `StepError::Input`, before any work). Debug builds check the device table against `PageMap`
  before every feed and step.
- Views: `slot_view` of a paged pool shares the pool's table from the slot's first entry (`CudaCache::tab0`);
  `retarget_view` moves `tab0`; `adopt` of a slot's own view copies nothing, a plain cache's is copied a page
  at a time through the table. The `Lm` calls on a view take no pages (infallible), so the engine reserves the
  solo run's positions (`lend_solo`: prompt + n_gen, at most the cap; idle prefixes reclaimed LRU) and releases
  what it didn't use (`end_solo`, `adopt`); `admit` releases the slot's tail past the reused prefix.
- kvio `Rows` take a page list (`tab`); `save_kv`/`load_kv` work on a paged view (the table row read back,
  up to the sink). The image layout and file format don't change: a paged slot's image is a plain cache's.
- `BatchLm`: `reserve`, `release`, `pages` (free/total/held per slot), `new_pool_paged`.
- Kill switch `AXON_PAGED_KV=0`: the plain pool (slot s at rows `s x ctx`, null table), the code on main.

Stage 3 (`serve.rs`, `engine.rs`, `ops.rs`, `lm.rs` placement):
- Plan (`paged_plan`): the pool's and the solo view's scratch (sized by the cap), POOL_SPARE, then every byte
  in pages, at most a page per position of every slot (so a small `--ctx` leaves room for the Q6_K copy as
  before). Up to 16 slots by default (a slot costs a table row and a logits row; `--parallel N`: N). The cap
  is the context, at most what the pages hold (binary search: a longer cap's scratch leaves fewer pages).
- Placement (`Placing::paged`): placed automatically, the whole model goes on the GPU if it fits beside an
  8192-token cache, instead of splitting for a cache of the whole `--ctx` (the pool takes what is left).
- Admission by pages (`can_admit`): the prompt's pages past the prefix the slot keeps, plus the pages the
  prompts being prefilled still need, plus a growth page per running request, against free pages and idle
  slots' (reclaimable) ones. Otherwise the request waits in the queue: no 500 for pages.
- Prefill back-pressure (`feedable`): a chunk feeds only what has pages beside a page per running request.
- Growth before each step (`grow`), oldest request first: reclaim idle prefixes, then unfeed the youngest
  prompt being prefilled, then preempt the youngest running request by recompute (back to the prefills with
  its tokens so far and its sampler; cache reuse == fresh prefill, so its output is unchanged). The oldest is
  never preempted.
- Banner: `KV: P pages x 64 = T tokens over up to S slots (cap C)`. `/slots`: `pages_used` per slot,
  `pages_free`, `pages_total`, `page_tokens`.

## What didn't work / notes
- (Caught reading the code, before any run.) The first stage-3 plan sized the cap in one step (pages at the full context's scratch, then the cap cut to
  what they hold): a shorter cap's scratch frees more pages than that, so the cap came out short (14B q8: the
  pages for ~18k tokens, a cap of ~10k). Now a binary search for the longest cap the pages hold.
- gemma3: a paged slot view decodes through `attn_split_w_256_pg`, which the #64 log measured at 0.942x the
  plain kernel (tg128). So gemma3 serve's single-stream decode pays that by default; `AXON_PAGED_KV=0` gets the
  plain pool back. Not fixed here (the kernel's cost is unexplained in #64 too).
- The pool takes the memory the Q6_K prefill copy used to get at the default context (the copy is made from
  what is left, as before): 7B serve at the default context has no copy now, so its prefill is slower than
  main's there; with a small `--ctx` the pool is at most a page per position of every slot and the copy fits
  as before. A trade for agents per card, measured below where the gates ran.
- Preemption is by recompute only (stage 4 adds preempt-by-store once kvstore is wired in). Admission
  reserves a request's prompt pages, not its generation, so a burst of long generations preempts.
- Prefix pages are per slot (no sharing between slots: the swarm's shared 20k prefix is held once per slot
  that has it).
