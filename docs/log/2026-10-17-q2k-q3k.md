# Q2_K, Q3_K (and IQ4_NL) on CPU and CUDA  (PR #72)

- Date: 2026-10-17. Branch: feat/q2k-q3k. Base: main d2e8eaf. Status: open
- Pick / design: roadmap long-term goal "2–3-bit weight types" (Kimi K2 / DeepSeek V3 at ≈ 250–380 GB; today a
  32B at Q3_K_M ≈ 15.9 GB or Q2_K ≈ 12.3 GB where Q4_K_M is 19.9 GB). Follows #22's pattern (Q5_K / Q4_0).

## What changed
- **CPU** (`src/quant/k23.rs`, `src/quant/iq4nl.rs`): dequant = ggml's `dequantize_row_q2_K / q3_K / iq4_nl`
  bit for bit. Integer dots against the Q8_K (Q2_K, Q3_K) or Q8_0 (IQ4_NL) activations: exact integers per
  block, then a fixed float step per block (Q2_K: `dx (d S - dmin M)`; Q3_K: `dx d S`; IQ4_NL: `d dx s`).
  Scalar, AVX2 (one token, four tokens, decode rows with prefetch) all give the same bits. Per-row layout (no
  r8 repack yet). `SUPPORTED_TYPES` gains Q2_K, Q3_K, IQ4_NL; the gguf type table gains IQ4_NL.
- **Why IQ4_NL:** llama.cpp quantizes rows that aren't a multiple of 256 (the 0.5B's 896) to IQ4_NL in Q2_K and
  Q3_K files, so bartowski's 0.5B Q2_K / Q3_K_M don't run without it. 32-value blocks, Q4_0's layout with a
  16-entry non-linear table. File labels vs content: the 0.5B "Q2_K" has **no Q2_K tensors** (IQ4_NL, Q3_K
  ffn_down, Q5_0, Q8_0) and the 0.5B "Q3_K_M" has **no Q3_K tensors** (IQ4_NL, Q4_K, Q5_K, Q5_0, Q5_1, Q8_0).
  Real Q2_K tensors are only in the 7B Q2_K here (Q3_K in it and in the 1.5B Q3_K_M, Llama 1B Q3_K_L, 7B Q3_K_M).
- **CUDA, ext module only** (`-DAXON_EXT_TYPES`, `Kernels::module_ext`; `needs_ext` picks it): `deq_q2_k /
  deq_q3_k / deq_iq4_nl`, decode GEMV `blk_q2_k / blk_q3_k / blk_iq4_nl` (8 lanes per 256-block, 8 values ×
  4 sub-blocks a lane; IQ4_NL via a `__byte_perm` table), `gemv_ref` cases. Canonical order (decode.cu "Row dot
  products"): Q2_K is Q4_K's pair with 16-value groups (`M = Σ m_g bsum16_g`, each lane's part of bsum16 by
  dp4a with ones); Q3_K is Q6_K's pair; IQ4_NL is Q4_0's.
- **Batched:** new kernels `gemm2{,s}_{q2_k,q3_k,iq4_nl}`. Q3_K and Q2_K are register-staged into Q6_K's
  shared-memory layout (int8 values, 16 int8 scales, d as f32), so Q6_K's mma16 products do them; Q2_K also
  stores its mins and dmin, and gets `M` from an all-ones-A mma16 per 16-value group. IQ4_NL is staged like
  Q4_0 through the table. Small batches (nb ≤ 16) take gemvn (no gemvm, as Q4_1/Q5_1). gemmh (Hopper) is
  Q4_K-only and untouched. Host: `batch.rs` type tables only (NTYPES 11, `type_index`, kernel names),
  `gemm2_smem`, type gates in `qwen2.rs` / `mod.rs` / `stream.rs`.

## Why
Every Q2_K and Q3_K_S/M/L GGUF was refused at load. These are the types that make 14B/32B fit 12 GB and that the
2–3-bit frontier MoE files use.

## Costs
- NVRTC: the six new `gemm2{,s}_*` kernels are in prefill.cu, which both kernel builds compile, so the
  first run after this change compiles more (one time; the kernel cache keeps it). ptxas time on sm_120 for the
  whole source went from 68.0 s to 77.3 s with the four Q2_K/Q3_K kernels (local nvcc -Xptxas -v sum, ESTIMATED
  for NVRTC); the two IQ4_NL ones are Q4_0-sized. Gating them behind `AXON_EXT_TYPES` is a possible follow-up.

## What didn't work / notes
- The first GPU-vs-CPU logits check reused the Q4_K_M-tuned flip budget (≤ 2 flips over 0.5) and failed on the
  1.5B Q3_K_M (3 flips, 0.55–0.81). The products were exact against gemv_ref in that job, but on synthetic
  matrices only (`gpu_products_match_reference_bits`); the CPU disagrees with itself more on that file (11/198
  top-1, KL 1.23e-2, 1.6x the 1.5B Q4_K_M's 7.8e-3; only its Q4_K/Q6_K rows differ between the CPU's two kernel
  sets, so this measures the model's sensitivity, not Q3_K) than the GPU does with the CPU (10/198, 1.13e-2).
  A first loosened bound (flips below the CPU's max |dlogit|, top-1 floor 90%) couldn't fail; review replaced it
  with `assert_graded`'s structure scaled by the CPU's self-spread (see `gpu_logits_match_cpu_q2k_q3k`), and
  `gpu_products_real_weights_q2k_q3k` checks the products on the files' real Q2_K / Q3_K / IQ4_NL tensors.
  The Q2_K/Q3_K tests now assert that every new type was covered when the files are present.

- The 0.5B "Q2_K" GPU vs CPU logits had one top-1 flip of margin 0.95 (twice on sm_120: d5d0, e746). On the
  test's 198 positions (`dump_logits_positions`): llama.cpp CPU vs CUDA flips ≤ 0.15 on this file (3.48 on the

  attention (another in-contract order, same weight kernels; it flips other near-ties, 0.53 / 0.59 instead).
  Attention-order noise, not a product deviation (products exact on real weights; compute-sanitizer memcheck clean,
