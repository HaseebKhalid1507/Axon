# RAM checks, round 2: the loader's conversions checked first, a split needs its larger step (#208, #209)

- Date: 2026-11-06. Branch: fix/ram-checks-2. Base: main 2aec1e5. Status: open (PR #215).
- Follows #206 (#183, #184, #185: docs/log/2026-11-06-ram-checks.md). Both issues were filed from #206's review and
  its real-cap run.

## What changed
- **#208, `safetensors::load`: the converted tensors are checked before they're made.** The loader converts a
  checkpoint's BF16 tensors to F16 or F32 into an anonymous arena (`AUX`): every matrix of a BF16 checkpoint, and an
  FP8 checkpoint's embedding, head and vectors (the 0.5B's embedding and head, 2 × 151936 × 896 × 2 bytes = 519
  MiB). It did that before any RAM check, so under a cap the FP8 0.5B split was OOM-killed at 765 MiB and below
  (#206's real-cap run, 1106-105219-0faf) before #184's check could read anything. `load` now estimates the
  conversion (`ConvNeed`: the arena in 2 MiB pages, the same `map_anon` length, and the conversion threads' read
  buffers: one piece of at most `PIECE` elements each, never more than the pieces) and refuses before mapping the
  arena (`conv_verdict`). The refusal is #185's form: the need and its parts, the bound, then the way out. The
  conversion happens on every device (the GPU uploads the converted tensors), so it's more free RAM, and for a BF16
  checkpoint its GGUF, which is read from the file. The tolerance is the memory cgroup's charge batches only
  (`model::conv_tolerance`: 256 KiB a CPU, 2 MiB on bella's 8-CPU job slots), not the CPU model's
  (`model::ram_tolerance`, 32 MiB more). A conversion gives nothing back before its peak, and its estimate is exact
  (below). The first candidate (f0e0bd6) used the CPU model's, and under a real cap that tolerance let through caps
  the conversion was then killed in.
  - **The CUDA context.** The CLI makes it on a background thread at start (`cuda::preinit`), alongside the load.
    Its host memory, charged after a check that read the RAM without it, would turn the check's margin into an OOM
    kill. `avail_settled` reads the RAM, and when it's within 1 GiB of the need, waits for the context
    (`cuda::settle`) and reads it again. Further from the edge, the load and the context still overlap.
- **#209, `model::dense_verdict`: a split's need is its larger step, not the sum.** The GPU half's upload (its
  staging: the page-locked ring, or the largest matrix it converts to Q8_0 on the host) is done before the CPU half
  is built: the ring is dropped before the conversions start, and each conversion's buffer before the next. #206
  added the two. The need is now `max(staging, (CPU half + KV floor − the GPU half's credit)⁺)`, each step with its
  own residents: the credit (the GPU half's anonymous bytes, handed back as they go up) is set against the CPU half
  only, as before, since the staging peaks while they're still held. The `--ctx` the refusal names is the CPU half's
  (none when the staging alone is over the room). The message says it's the larger of two steps.
- **The FP8 CPU arena counted whole** (found while setting up #209's 7B run). `dense_ram_need_keep`'s growth (what a
  load commits beyond the bytes it replaces; `dense_load_bytes` uses it when the model isn't file-backed) took every
  matrix's source as anonymous memory that `release` hands back. A safetensors checkpoint isn't file-backed (its
  converted tensors are anonymous), but an FP8 checkpoint's matrices are read from the file. Their F8S rows are all
  new memory, so the CPU model's need and a split's CPU half were the rows' scales alone. On the 7B at 20 of 28 GPU
  layers, that's about 1.8 GiB of rows checked as nothing, and with the max above the check would have been the
  staging alone. `Model::anonymous(t)` says which tensors' bytes go back; only theirs are credited.
- **#209's nits.**
  - `scripts/fp8cap.sh`: #206's real-cap script, in the repo, generalized (any two binaries, any checkpoint and
    split; `floor` and `steps` modes, below). Its comment said the FP8 0.5B's head is tied. The config ties it, but
    the file carries its own `lm_head`, and that's what the split converts.
  - The FP8 module's split refusal (fast mode, sm_89 and up: natively, FP8 runs every layer or none) went through
    the plan, whose refusal the split wraps as a VRAM shortfall, ending ", or fewer --gpu-layers". Fewer is refused
    too. `hybrid::f8_split_refusal` now refuses it before the plan, with what works: `--numerics exact` (its Q8_0
    form splits), and for a split chosen with `--gpu-layers`, `--gpu-layers N` with every layer, if the GPU has room.
  - The CPU model's refusal of an FP8 checkpoint in fast mode named `--gpu-layers N`, which leads there. It now names
    `--gpu-layers N and --numerics exact` (`GpuWays::exact`; `check_ram_dense` takes the Backend's numerics mode).
- README (CPU memory limits), CHANGELOG.

## How it was verified
Each fix's test fails before it. The expect-fail tree is the candidate with five product changes reverted and the
tests kept: no conversion check (the RAM is still read, the verdict ignored), the sum, `GpuWays::exact` always
false, no `f8_split_refusal`, and the growth crediting every source.
- `safetensors::tests::conversion_refused_before_it_is_made` (tiny checkpoints, CI): the RAM is asked for the
  conversion's need exactly (the test recomputes it from the tensors: the `AUX` arena and the buffers); a byte under
  the need less the tolerance is refused, at it loads, with no RAM figure it loads, and a header-only load (`axon
  info`) never asks. The BF16 refusal names its GGUF; the FP8 one doesn't.
- `safetensors::tests::fp8_conversion_need_of_the_checkpoint` (the FP8 0.5B): the arena is the embedding's and the
  head's F16 bytes plus the vectors (under 8 MiB more), refused a byte under the edge, loaded at it; refused at the
  CPU model's tolerance's edge. `model::tests` (the dense tolerance's case): the conversion's is that less
  `DENSE_CHECK_TOLERANCE`.
- `model::ram_dense_tests::split_refusal_wording_and_cap`: #184's case is now 2.34 GiB, the larger step (it was the
  sum, 2.41 GiB), refused a byte under the edge and through at it. A 7B FP8 split's shape (a 552 MiB staging, a 1039
  MiB credit): through at the CPU half's need alone. A CPU half the credit covers: the staging alone. A staging that
  fits: the CPU half's `--ctx 4608`, where the sum named none.
- `hybrid::tests::hybrid_fp8_split_needs_the_larger_step` (GPU, the FP8 0.5B at 1 of 24 GPU layers, `--ctx 512`):
  both steps are over the tolerance (figures below), the split is refused a byte under the larger and built at it,
  and the built CPU half is the estimate.
- `safetensors::tests::tiny_fp8_ram_arena_without_repack`: + a CPU half's growth is at least its e4m3 bytes (it was
  their scales).
- `safetensors::tests::tiny_bf16_ram_refusal_names_no_gpu`: + the tiny FP8 checkpoint in fast mode: `GpuWays`
  `exact`, and the refusal names `--gpu-layers N and --numerics exact`; a BF16 one in fast mode still names no GPU.

  `hybrid_split_plan_refusal_keeps_its_wording`): the exact refusal for a split chosen with `--gpu-layers` and for
  an automatic one, before the stream's plan too.

### Where the floor's kills came from (f0e0bd6, job 1106-142807-b4b3)
The first floor run at f0e0bd6 (1106-141446-e7d6) had the candidate refuse at 703 MiB and below but OOM-killed from
719 to 767 MiB, 64 MiB above a refusal (the script's band is 48). A diagnostic build (f0e0bd6 plus a stage trace of
the cgroup's unreclaimable memory, not merged) at 8 MiB steps from 783 down to 719 MiB showed two bands:
- 719–743 MiB: killed converting. The check had passed on the tolerance alone (at 719: 530.0 MiB available + 34 ≥
  554.0 needed). The conversion grew the cgroup by 554.7–555.0 MiB, against the estimate of 554.0, at every cap that
  got through it. Hence the conversion's own tolerance above.
- 751–767 MiB: killed loading the CUDA kernels' module (`Kernels::module_for_mode`): +24.5 MiB of anonymous memory
  after the conversion check and before the split's, counted by neither. 775 and 783 got through it and the split
  refused (4.9 and 12.3 MiB available). That's #184's class (host memory a CUDA run commits before a check), filed as
  #217, not fixed here.
- Nothing else between the checks moved by more than 1 MiB: the tokenizer, the FP8 value scan, opening the GPU. The
  CUDA context was in at the conversion check at every cap (about 76 MiB of kernel memory). Main at 711–735 MiB was
  killed every time (e7d6's one rc 2 for main at 719 wasn't seen again in four runs).
- At 8af3b59 (1106-171946-ef01) the kills landed where these figures put them: refused through 735 MiB, killed at
  751 and 767 (the module), the split refusing from 783.

  waits for it near the edge.
