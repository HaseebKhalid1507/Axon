# 128 × 64 Q4_K / Q5_K GEMM tile (`gemm2t`, r17 pick 1)

- **Date and branch:** 2026-10-19, branch `feat/gemm-128x64`, stacked on `feat/prefill-wave-split` @ 05b7b8d (#92).
  #92's `gemm_cost` has to learn the new tile shape. Merge main into this branch once #92 lands.
- **Spec:** `r17-gemm-ablation.md` (Spike), the step-0 ablation study behind this change.
- **Numerics:** the bits are unchanged, so `NUMERICS_VERSION` is not bumped. Each output's K chain stays in one thread,
  in block order. S and M are the same exact integers, and the float ops are the same.

Labels: **MEASURED** (job log cited), **CODE**, **ESTIMATED**.

## Why

r17 ablated `gemm2s_q4_k` on avante (RTX 4050 Laptop, sm_89).

- **The main loop is not bound by** any of these:
  - mma throughput: replacing the mma with LOP3s moved it −4…0 %;
  - L2 or DRAM data: L2-resident copies moved it ±2 % on gate;
  - the cp.async wait: ±1 %;
  - dequant ALU: +8–10 % for all of it.
- **The biggest single cost is the cp.async activation fill.** Skipping it alone gives +19 / +32 / +16 % on
  gate / down / gu (MEASURED). The weight fill gives +11 / +13 / +7 %.
- **Why the old 64 × 128 tile didn't help.** It halves *weight* fill per MAC and was flat (r16 step-0).
- **What this tile does.** A 128-row tile halves *activation* fill per MAC instead.

## What changed

- **Kernel (CODE, prefill.cu).**
  - `gemm2_t` takes `WR` row-warps:
    - `WR = 2`: today's kernels, unchanged.
    - `WR = 4`: 4 × 2 warps, each 32 × 32, so 128 rows × 64 tokens. Two stages, because three don't fit 99 KB of shared
      memory: 82,432 bytes.
  - New kernels: `gemm2t_q4_k`, `gemm2t_q5_k`, and `gemm2t_q4_k_gu` (64 rows of gate + 64 of up; the exchange
    generalised).
  - The warp work is `gemm2_q4_k`'s.
  - Copies use `G2Fast`: per-thread addresses computed once per block, so a chunk costs one IMAD.WIDE + LDGSTS.
  - **Registers (nvcc 13.4 ptxas, sm_89):** 246 / 253 / 246, with 0 spills.
- **Coverage.** Only the raw-row types (Q4_K, Q5_K) get the tile. The register-staged types (Q6_K, Q8_0, Q5_0, Q4_0,
  Q4_1, Q5_1, Q2_K, Q3_K, IQ4_NL, Q6K8) stage 64 rows per 256 threads (`g2_item`), so a 128-row tile is not free for
  them. The kernel `static_assert`s this.
- **Routing (CODE, batch.rs).** `tile_t(rows, br, nb, sms)` picks gemm2t where its waves, weighted at
  `TILE_T_TIME` = 82 % per MAC, cost less than gemm2s's:
  - it is used for the big products on every GPU;
  - it is not used for, e.g., the 7B's 512-row k / v at nb 1024 on 128 SMs, where halving the blocks idles SMs;
  - the same rule drives `gemm_cost`, so the wave split models the tile it will run.
  - sm_90a's gemmh2 still takes precedence where it applies.
- **Switch.** `AXON_GEMM_TILE=64` keeps gemm2s everywhere, as before.
- **Tests.**
  - `gemm2_names` adds gemm2t for Q4_K/Q5_K, so `gpu_products_match_reference_bits` and the swiglu mode-2 test cover
    it.
  - The gate + up test also runs `gemm2t_q4_k_gu`.
  - `tile_t_picks`.
  - `wave_passes_shapes` runs with `tile_t` both off and on.
  - New: `cuda_gemm_tile_bench` (ignored) and `AXON_PROF_TILE_AB` in `cuda_prefill_profile`.

## Method (avante is power-capped)

- **Power cap.** The RTX 4050 Laptop sits at its SW power cap (throttle reason 0x4, ~63–68 W) under these kernels. A
  short sample therefore inherits boost credit from whatever ran before it: in r17, two identical runs of the same
  kernel differed by 18 %.
- **`cuda_gemm_tile_bench` controls for this:**
  - each sample is a 200 ms window of back-to-back launches, after half a window of warm-up;
  - cases run in a shuffled order every round, 7 rounds, and the median is reported;
  - the SM clock is sampled by `nvidia-smi -lms 50` over each window; MAC/clk/SM is a sanity check, not a second
    measurement.
- Repeating a case in r17 agreed within 1 %. The per-sample spread is about ±4 %.

## Follow-up (r17 fix 2, step 0, MEASURED, avante job 1019-012104-a5b1, gemm2s)

This experiment skips copies within the activation fill. Δ is against the mean of two `full` copies: 14.60 / 13.72 /
14.25 TMAC/s.

| variant | gate | down | gu |
|---|---:|---:|---:|
| skip the whole activation fill | +18 % | +33 % | +15 % |
| skip the values (16 B cp.async) | +10 % | +23 % | +9 % |
| skip block sums + d (the 4 B cp.async) | **+8 %** | **+16 %** | **+7 %** |

- So a 16-byte-aligned bsum/d layout, with 2 cp16 per token instead of 8 + 1 cp4, is worth at most ≈ +8–16 % on gemm2s.
- In gemm2t its share halves. That is roughly +4–8 % on top of this PR (ESTIMATED).
- It would be a separate PR.
