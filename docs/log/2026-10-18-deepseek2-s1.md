# deepseek2 stage 1: MLA attention, router and shared experts on the GPU, routed experts on the CPU

- Date: 2026-10-18. Branch: feat/deepseek2-gpu. Base: main 953b886 (stage 0 merged as #79).
- Spec: `specs/r12-deepseek2.md` §2 (the latent cache, the new kernels) and §4 stage 1; the shape is #67's MoE
  split (qwen3moe's `--device cuda`: attention/router on the GPU, `{h, ids, w}` down, experts on the CPU, `y` up).

## What changed
- `--device cuda` runs deepseek2 (Moonlight, and by shape V3/K2): **attention, norms, the router, the shared
  experts, the dense lead layer(s), embedding and head on the GPU; the routed experts on the CPU** (llama.cpp's
  `-ot exps=CPU` / `--cpu-moe` layout). `crate::moe::MoeQwen3` drives either architecture (`new_mla`); the
  banner is the qwen3moe one (`moe: attention + router on the GPU (… GiB, ctx …), 64 experts x 26 layers on the
  CPU (top-6)`).
- New kernel module `src/cuda/mla.cu` (`Kernels::mla_module` = kernels.cu's dequantization + moe.cu's router
  logits/add + mla.cu, compiled on its own): the dense, qwen3moe and gemma modules and their cache keys are
  untouched.
  - `mla_kv_store`: the cache row of each token, `[rmsnorm(c[..lat]) · g | rope(c[lat..])]` in f16, into row pos.
  - `mla_qrope`: the queries' rope parts turned into the absorbed queries' tails.
  - `mla_heads_mv`: the per-head absorb (`Wk_b[h] q_nope_h`) and expand (`Wv_b[h] o_h`) products: a warp per
    matrix row and 8 tokens, the weights dequantized exactly (kernels.cu `deq`), f32 inputs (no 8-bit
    activations), one fma chain per (row, token) then a fixed xor tree.
  - `mla_attn` + `mla_attn_cmb`: the absorbed attention, all of a block's heads (up to 8) over one K tile of 32
    rows in shared memory (32 × 576 f16 = 36.9 KB, under the 48 KB default: no opt-in), Q·K per head by a warp,
    an online softmax across tiles in order, P·V over the same tile's first `lat` columns (V is K's prefix: no
    V tile). A token's rows are cut into **splits of 128 rows from row 0** (fixed: the split points are part of
    the bits), one block per (8 heads, token, split), then a combine per (token, head) in split order: decode's
    parallelism grows with the context (Moonlight at 4k: 2 × 32 blocks instead of 2). f32 throughout (CUDA
    cores; no tensor cores). A batched pass launches the attention in chunks of tokens whose partials fit 64 MB.
  - `mla_topk`: deepseek2's router after `moe_logits`: sigmoid (or softmax), `exp_probs_b` for selection only,
    renorm, then the weight scale (llama.cpp's order, the CPU's `Gate`).
- `src/cuda/qwen2/mla.rs`: a deepseek2 `CudaQwen2` has no `layers`; its `mla` holds the MLA layers (attn_k_b /
  attn_v_b as one matrix each, a head's rows its slice) and `head_dim` is the RoPE width (64), so the step's
  RoPE table, the embedding, the head and the batch scratch are the dense model's. The latent cache is the
  cache's `kv`: one array per layer, `[rows][576]` f16 (31.1 KB/token on Moonlight; `kv_cache_bytes`).
  `mla_step` (decode, captured graphs per segment) and `mla_tokens` (feed_batch / verify / prefill_logits)
  run **one code path**: `mla_layer` over nb tokens (nb = 1 in decode) with every matrix through `bgemm` and the
  batched norm/quantize kernels.
- Shared experts overlap the CPU: the round trip enqueues the router's copy down, records an event, then the
  shared experts (decode: their own captured graph per layer), waits for the event only, runs the CPU experts,
  and enqueues y up. Stream order keeps `x += shared` before `x += routed` in decode and batched passes alike.
- CPU half: `Qwen2::new_experts` builds deepseek2 with only the routed experts repacked (`deepseek2::build`'s
  `experts`); every other matrix stays in the mapping, unread. `moe_layer[_batch]` reach a deepseek2 layer's
  experts (`layer_moe`).
- Placement: `lm.rs` takes deepseek2 to the MoE backend (`moe_cpu_only` is gpt-oss only now). Refused on the
  GPU: `--kv q8` (no MLA q8 cache yet), head counts that aren't 1/2/4 or a multiple of 8, cache rows over 576.
  No paged KV for it (MoE ships without), as #67.

## Exactness
Decode == feed_batch == verify and prefill_logits == decode, bit for bit, by construction: every mla.cu kernel
works per token (a token's position from P in decode, from `start` in a pass; the attention's tiles start at
row 0 whatever the batch); the products are `bgemm`, whose kernels give a token the same bits at any nb (G3);
decode and batched passes call the same `mla_layer`. The head is the dense model's (decode `enqueue_head`,
batched `bgemm` + `argmax_b`: the dense G3 pair). Against the CPU it is graded, as the GPU always is.

## What didn't work / notes
- The first kernel-test round "failed" on the tests, not the kernels: the copied test RNG (`moe/tests.rs`'s)
  is uniform in [-1, 3), not [-1, 1) as its comment says; ×4 router logits then saturated the f32 sigmoid into
  exact ties (two experts both 0.99998946), which the GPU breaks to the lower index exactly as the CPU's `route`
  does but an f64 reference doesn't. Fixed the RNG in mla_tests.rs; the selection reference is now f32.
- Grading the fixture GPU vs the CPU directly (`compare` + `assert_graded`) fails both ways round: random
  weights, vocab 64 and near-tied routers everywhere make two correct 8-bit models disagree on 12 % of greedy
  positions. Against the f64 expanded reference both are measurable and the GPU is the closer one.
- The first attention kernel ran one block per 8 heads over all of a token's tiles: 2 blocks for Moonlight's
  16 heads whatever the context, so decode attention grew linearly with it (ESTIMATED ~8 ms/token at 4k
  positions). Replaced by the 128-row splits before any measurement of record.
