# H100 step anatomy kit: a serve step trace, two gemmh2 variants, feed_slot t0 (2026-10-24)

Roadmap item 1(a) ([Next: proposed order](../roadmap.md#next-proposed-order-outside-review-10-19-owner-decides),
outside review 10-19 §2.4): measure the H100's decode step per kernel, the cost of the per-256 drain on Hopper, and
one serve cell step by step, in ONE prebuilt-binary pod session. This PR is the Axon side of that kit; the runbook,
driver and pod scripts are in axon-devstack `runbooks/h100-anatomy/`. No pod has run yet (the session waits for
Haseeb's approval, ≈ $1).

## What changed

- **`AXON_SERVE_TRACE=FILE`** (`src/serve/engine.rs`, product code, default off). One JSON line per engine step that
  did work, appended to FILE: `t_ms` (since the trace opened), the step's wall `ms`, its prompt feeds (`feeds`
  passes, `fed` tokens, `feed_ms`), its decode pass (`rows`, mean `depth`, `dec_ms`; null without one), then
  `prefilling` and `running`. Host wall clock: `feed_slot` and `step` return once the GPU is done, so a pass's time
  is its kernels plus launches, and `ms` less both is the step's host work. `Batch::step` became a wrapper over
  `step_inner`: with no trace it is one `is_none()` branch; the two hooks (in `feed`, after `net.step`) are behind
  `if let Some`. On, it costs a `format!` and one `write(2)` per step (tens of µs against a ~50 ms C = 128 step,
  < 0.1 %): a traced cell compares to the untraced 10-19 one within noise. The arithmetic of the cost estimate in `feed` is unchanged (`us / (n * mid)` is the old expression
  split in two). Why: the review's ~9.6 s of a mix C = 128 cell that is "neither prefill nor decode kernel"
  (ESTIMATED from per-request data) should be confirmed before the merged pass and the scheduler fixes are judged.
- **`cuda_gemmh_bench`** (test-only): `gemm2t_q4_k` beside gemm2s / gemm2, and on sm_90a two kernels of a second
  module, `gemmh2nd_q4_k` and `gemmh2nd_q4_k_gu`, built from `gemmh2_variant_src(NoDrain)`: KERNELS with
  `gemmh2_t` patched so the S wgmma chains accumulate over the whole K in int32 (scale-d 0 only on block 0's first
  k32), M likewise, and the float epilogue runs once on the last block's scales. **Inexact by design, a bench
  only**: its speed over the exact gemmh2 is the upper bound of what the drain (the contract's only Hopper-specific
  cost, review §2.3) costs. It lives in `src/cuda/qwen2/tests.rs` under `#[cfg(test)]`, so no product path builds
  it; the kernel cache is keyed by the source, so its cubin can't be loaded for the real kernel. It keeps the
  per-block `wgmma.wait` (the RS A-fragments are refilled per block), so it bounds the drain's arithmetic, not that
  wait. `AXON_BENCH_VARIANTS` picks them.
- **A second variant, `gemmh2mg_q4_k[_gu]`** (research `hopper-exact-w4a8-20261024.md` §3.3, its E0' (a)): exact
  by construction. The sub-block scale is split 3 + 3 instead of 4 + 2 (sc = lo3 + 8 hi3; the pre-scaled quants
  q lo3, q hi3 stay ≤ 105, u8), so |Dlo|, |Dhi| ≤ 8 · 7 · 32 · 15 · 127 = 3,413,760 < 2²², S = 8 Dhi + Dlo is the
  same integer as before, and rn(S) is computed as `fadd(fsub(bits(0x4CC00000 + Dhi), 1.5·2²⁶), fsub(bits(
  0x4B400000 + Dlo), 1.5·2²³))`: both terms are exact floats, so the single rounding fadd is rn(S), what
  `cvt.rn.f32.s32` returns, with no I2F (16 results / clk / SM by the research note's citation, vs 128 for FADD).
  **The note's constant is wrong**: it writes 0x4D400000 with 100663296.0f, but 0x4D400000 is 1.5·2²⁷ (ulp 16);
  1.5·2²⁶ is 0x4CC00000. Proven three ways before any H100 time: `magic_i2f_is_cvt_rn` (host, IEEE f32, every Dhi in
  ±(2²² − 1) against 16 Dlo values both ways round, 268 M pairs, in every suite), `gpu_magic_i2f_is_cvt_rn` (the
  device's `__fsub_rn` / `__fadd_rn` / `__int2float_rn`, 134 M pairs, any GPU), and on the H100 itself
  `gpu_gemmh2_magic_matches_reference_bits` (gemmh2mg and gemmh2mg_gu against gemv_ref bit for bit: the real kernel's
  shapes plus an adversarial fixture at the proof's bounds, every scale / min 63, quant 15, activations ±127, |S| up
  to 30.7 M > 2²⁴ where the conversion rounds). Not routed anywhere: a measurement for item 2.
- Both variants' kernels are renamed (gemmh2nd_*, gemmh2mg_*) so a profiler tells them apart;
  **`gemmh2_variant_patches_apply`** (no GPU, in every suite) checks every patched line exists exactly once in
  `gemmh2_t` and nothing before it changes; `AXON_VARIANT_SRC_DIR=DIR` writes both sources (the kit compiles them
  offline into the pod's sm_90a kernel cache, which also proves they compile for sm_90a without an H100).
- **`cuda_i2f_bench`** (ignored): I2F vs the magic form in results per clock per SM (clock64 per block, one block
  per SM), to check the research note's 16 / clk / SM.
- **`pool_feed_cost`** (ignored, `cuda::qwen2::slots::tests`): `feed_slot`'s per-pass fixed cost t0, the
  shortest-first scheduler spec's first unmeasured number (`specs/sched-sjf-token-budget.md` §10.1): n tokens fed into
  one slot at a depth, wall clock with a sync (what serve's `feed` sees), median of 15, at n 1 … 512 and depth
  0 / 600 / 4,096, and the least-squares t(n) = t0 + c n.
- `cuda_gemmh_bench` takes `AXON_BENCH_VARIANTS`, `AXON_BENCH_SHAPE` and `AXON_BENCH_KERNELS` (the kit's ncu run
  profiles only the gemmh2 kernels at gate 3,584 × 18,944, nb 1,024).
- **`step_trace_lines_are_json`**: a trace line parses as JSON with every field, nulls without a decode pass.

`pool_step_cost` already prints per-segment times from events and needed no change; it had only ever run on a 4090
at nb ≤ 64 ([c-curve log](2026-10-18-c-curve.md)). The kit runs it at nb 1–256, depth 600 / 4,096.

## What it doesn't do

No numbers from the H100 yet: those come from the session, in a follow-up log entry. MEASURED on bella so far:
only that the magic conversion is bit-identical on the host and the device (above). The inexact variant bounds
only the drain's arithmetic; a double-buffered RS pipeline (waiting one block late) is item 2's work, not a bound.

## Update 2026-10-26: merged with main 8508a75 (#131's step budget)

rewrote the same `feed` / `step` lines. Resolution: main's step-budget code everywhere, the trace hooks on top.

`cost.learn_feed`. `step` is the trace wrapper around main's body (one `is_none()` branch when off). The decode pass's
