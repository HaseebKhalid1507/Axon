# Serve ops pack: --api-key, /metrics, /slots, --max-prompt-tokens, --slot-idle-ms  (PR #61)

- Date: 2026-10-17. Branch: feat/serve-ops. Base: main cf68e9d (after #57). Status: open.
- Pick / design: r10 scope, round M2 (specs/r10-scope.md §3.4): the operating surface a LAN deployment needs
  on day one, llama-server parity.

## What changed
- `--api-key KEY` / `AXON_API_KEY`: every route except `GET /health` needs `Authorization: Bearer KEY`. The
  scheme is case-insensitive and the token is compared in constant time (for a given length). Without it the
  answer is a 401 with OpenAI's error shape (`code: "invalid_api_key"`) and `WWW-Authenticate: Bearer`. CORS
  preflights (`OPTIONS`) stay open: browsers send them without credentials, and they answer with headers only.
- `GET /metrics`, Prometheus text 0.0.4: `axon_requests_total{route,status}` (the route label comes from a fixed
  list; anything else is `other`), generated, prompt and cached prompt tokens, in-flight requests, queue depth,
  slots busy/free, idle evictions, refused prompts, and the histograms `axon_ttft_seconds` and
  `axon_itl_seconds` (the gap between a request's text events, about one token each). There are no host-store
  hits: serve has no KV store yet (M1). That counter goes in with it.
- `GET /slots`: `{ctx, slots: [{id, busy, held_tokens, request_id, age_ms}], solo: {...}, queue_depth}`. `solo`
  is the engine's single-request cache.
- `--max-prompt-tokens N`: a longer prompt gets a 400 (`context_length_exceeded`, the param named) before it is
  queued. Past N times the longest token's bytes, it is refused before tokenizing.
- `--slot-idle-ms MS`: a stream whose client stops reading is cancelled through the disconnect path (the cancel
  flag; the engine reaps it at its next step and frees the slot). It is detected in two ways. On Linux, bytes are
  waiting unacknowledged (SIOCOUTQ) and the acknowledged count hasn't moved for MS. Elsewhere, a write blocks for
  MS (the socket's write timeout during the stream). A client that reads slowly keeps the count moving and is
  not affected. A stalled client can't be told from a slow one until its receive window is full, so the clock
  starts there.
- The request field `priority` is accepted and ignored (api.rs doc table). Unknown fields were already ignored.
- Where the hooks are: `src/serve/ops.rs` (new: auth compare, metrics registry, slot view, stall detector).
  `http.rs`: 401 reason; `Conn` records the last status and the bytes written. `serve.rs`: Opts/Shared fields,
  route() auth plus the two routes, completion() cap, and an `Events` wrapper around the connection's event
  receiver (TTFT/ITL/usage/stall) that replaces `next_event`. `engine.rs`: one read-only `Batch::slot_states()`;
  the engine loop publishes it once per iteration. `Engine::run` publishes the solo cache's state before and
  after a job. Nothing in sampling, kernels, plan/starve or admission changed.

## Why
Spec §3.2: anyone who exposed serve on a LAN got no auth and saw nothing of the server but `/health`. A chatty or
stalled client could hold a slot until `WRITE_TIMEOUT` (60 s) after its socket buffers filled, and a huge prompt
could only be refused by `--ctx`.

## Results
- Corrected after review: the first figure (1.11 s, `--slot-idle-ms 500`) and the test both use a client with a
  tiny receive buffer (2-4 KiB `SO_RCVBUF`), so the idle clock starts almost at once. That is not the real-world
  bound. A stopped client can't be told from a slow one until its receive window is full, so with a default
  window (~128 KiB, autotuned) the clock starts only after roughly 500+ tokens of SSE (200-300 B each), and a
  reply shorter than that simply finishes into the buffers.
- MEASURED (fuzz_serve.py --ops, bella CPU, 0.5B at ~125 tok/s, `--slot-idle-ms 1000`, job 1017-061629-9526),
  from the client's last read to the slot freed:
  | client receive buffer | tokens generated meanwhile | time |
  |---|---|---|
  | `SO_RCVBUF` 4 KiB | 202 | 1.7 s |
  | default (Linux autotuned) | 792 | 6.3 s |
  The 4 KiB case still runs ~200 tokens: the server's own send buffer fills before acknowledgements stop
  mattering. ESTIMATED from the 792 tokens: a few seconds on a GPU stream at 100+ tok/s, ~25 s at 30 tok/s.
- MEASURED (test `serve_slot_idle_frees_a_stalled_stream`, 300 ms through `Opts`, 2 KiB `SO_RCVBUF`): freed
  within 300 ms + 2.5 s slack of the window filling (the assert). Without the flag, the same client still holds
  the slot 1.8 s later.
- No speed effect expected. The per-step cost is one mutex and a Vec of `slots` small structs; the per-event cost
  is two atomics and a histogram bucket. Not benchmarked: decode steps are milliseconds and this is far below noise.

## What didn't work / limits
- A write timeout alone wasn't enough: Linux autotunes the send buffer up to 4 MiB, so a stopped client could
  absorb minutes of tokens before a write blocked. Watching acknowledgements (SIOCOUTQ) catches it once the
  receive window closes.
- `/slots` and the busy gauges are a snapshot from the engine's last loop iteration: a slot freed mid-step shows
  free one step later.
- ITL is per text event, not per token. A token that completes no UTF-8 character, or that the stop matcher holds
  back, merges into the next event's gap.

## Update 2026-10-17: review fixes (shady, r10 thread msg-ca15ead1)
- `AXON_API_KEY` is trimmed (a docker/k8s secret's trailing newline used to make every request a 401 with
  nothing to say why). Set but blank is a startup error. stderr logs `api key: on (from AXON_API_KEY|--api-key)`
  and never logs the key. `start()` refuses an empty or blank key (a library caller's `Opts`; the CLI already
  did), and `authorized()` never accepts an empty token or an empty key.
- `--slot-idle-ms` has a floor of 1000, and lower values are refused with an error: delayed ACKs (40-200 ms) and
  retransmit backoff would evict live clients. Tests set less through `Opts`.
- The stream's write timeout is `min(idle, 60 s)` (it was `idle`), so the flag never makes a blocked write wait
  longer than without it.
- SIOCOUTQ (0x5411) is compiled only for Linux on x86, x86_64, arm, aarch64, riscv64, s390x and loongarch64 (the
  asm-generic ioctl numbering; mips, powerpc, sparc and alpha differ). Elsewhere stderr warns at startup that
  only blocked-write detection is active. Where the probe is compiled in but fails at run time, the server warns
  once.
- `Expect: 100-continue` before auth: fixed. A request without the key gets the 401 (with `invalid_api_key` and
  `WWW-Authenticate`) before `100 Continue` would invite its body. (Corrected in the follow-up
  `2026-10-17-serve-ops-followup.md`: that alone didn't stop a client that sends its body without `Expect`;
  the follow-up refuses every body-carrying request without the key right after its head, and the body is
  never buffered. `linger` still drops up to 2 s / 4 MiB of what was sent, so the 401 survives.) `Conn::gate`,
  test `serve_api_key_before_100_continue`, fuzz case `auth:expect-100-no-key`.
- TTFT is measured from the request's arrival (its body read: tokenizing and queueing count), as the HELP text
  now says. Only a text event counts as a first token; a Done without text doesn't.
- Documented: `--max-prompt-tokens` counts the whole rendered prompt (template and tool-schema tokens), and
  exactly N is allowed. `/slots` `solo` becomes slot 0 once #60 lands (#60's builder folds it in; doc comment
  on `SlotsView::solo`).
