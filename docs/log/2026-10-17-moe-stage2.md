# MoE stage 2: attention + router on the GPU, experts on the CPU  (PR #67)

- Date: 2026-10-17. Branch: feat/moe-s2. Base: main ca44e67 (stages 0–1 from PR #63). Status: open, not merged.
- Design: r11 MoE spec (`specs/r11-moe.md` §2.1–2.4, 2.6, §3.1, §4 Stage 2). Roadmap Scale item 7.

## What changed
- **`src/cuda/moe.cu`** (new; its own NVRTC module, `Kernels::moe_module`, loaded by the MoE backend only, so
  the dense models' kernel source, cache key and cubin are unchanged):
  - `moe_logits`: one warp per (token, expert), 8 experts per block, grid (n_expert/8, nb). Each block applies
    the FFN RMSNorm to its token's residual (sum of squares by a fixed tree, then rmsnorm_quant's per-value ops)
    into shared memory, and block 0 stores it (`h`, f32, for the CPU experts). Lane l sums `W[e][c] * h[c]`
    (multiply then add) over c = l, l+32, … ascending, 8 loads in flight; the lanes fold by a fixed xor tree.
  - `moe_topk`: one block per token: softmax (max and sum by fixed trees, `expf`), k rounds of tree argmax with
    `(p desc, index asc)` (ties go to the lower expert index), `w_i = p_i / max(Σ w, 6.103515625e-5)` (llama.cpp
    CPU's division and clamp).
  - `moe_add`: x += y. Nothing depends on the batch size: a token's normed state, ids and weights are the same
    bits alone or in a batch of 512 (unit test).
  - The first version (one block of 128 threads per token, one thread per expert summing all 2048 inputs) cost
    53 µs per token per layer (latency-bound loads); the warp-per-expert split cut the whole GPU segment of a layer
    from 150 to 50 µs (MEASURED, Pruned-2B). The spec's "no warp split" was about a fixed order; this order is
    fixed too (not bit-equal to the CPU twin's logits, which nothing requires).
- **`src/cuda/qwen2.rs`**: `LayerW::ffn` is `Ffn::{Dense{gate,up,down}, Moe{router}}` (model.rs `Ffn`'s mirror;
  `dense()` / `mats()` accessors); `plan(.., moe)` and `with_kv_moe` upload a qwen3moe's attention, norms, routers
  (f32, `[n_expert][dim]` in `vecs`), embedding and head; every other GPU entry (split, pipeline, draft model)
  still refuses a MoE. `enqueue` is split, by pure code motion, into `enqueue_input` (embedding, RoPE table),
  `enqueue_attn` (a layer's attention sub-block) and `enqueue_head`: the dense step launches the same kernels
  with the same arguments in the same order.
- **`src/cuda/qwen2/batch.rs`**: `layer` = `attn_half` + `ffn_half` (code motion, same launches); a few items
  `pub(super)`.
- **`src/cuda/qwen2/moe.rs`** (new): `MoeBufs` (router output and y on the device, pinned twins, per-segment
  graphs), `moe_step` (decode), `moe_pass` / `moe_tokens` (verify, prefill: batched attention, the experts over
  the whole pass), `AXON_MOE_PROFILE=1`.
  - Decode: per layer one captured graph (`moe_add` of the previous layer's y, the attention, the router), one
    D2H of `{h, ids, w}` (dim + 2k floats), the CPU experts, one async H2D of y; the last segment adds y and runs
    the head. So the host round trip is two copies, a stream sync and one graph launch per layer.
  - Batched passes launch kernel by kernel (as dense batched passes do); the host reads and writes the pinned
    buffers in place.
- **`src/moe.rs`** (new): `MoeQwen3: Lm` = the GPU half + `Qwen2::new_experts` (the experts only, r8-repacked; no
  head, the attention matrices left in the mapping and never read). The experts get the GPU's routing:
  `Qwen2::moe_layer` (decode) / `moe_layer_batch` (`src/model/moe.rs`: stage 1's kernels, routed by the caller;
  the CPU-only path is unchanged).
- **`src/lm.rs`**: `Backend::Moe` / `BackendCache::Moe`; `--device cuda` on a qwen3moe builds it (`fit` and the
  context as for the whole-GPU model; `--gpu-layers` below the layer count is refused: no layer split).
  identity (`cuda+cpu experts`), serve banner, kvsave (no cache image) arms.
- `axon info` / the refusal text say what runs where now. README, roadmap.

**Decode profile** (`AXON_MOE_PROFILE=1`, per layer, Pruned-2B = the 30B's layer shapes; segments synced for the
profile): GPU segment (y add + attention + router) **45–48 µs** short context, **77–80 µs** at ~8.1k; copy down
5 µs; unpack 0.1 µs; experts 267–350 µs (helped by L3: only 3 layers' experts); y up 2.4 µs. 4x0.6B: GPU 34–37 µs,
experts 4.41 ms per 28 layers = ~76 GB/s over its ~12 MB of active r8 experts per layer (DRAM-bound: its active
set doesn't fit in L3). Unprofiled tg: Pruned-2B 742, 4x0.6B 178 tok/s.

**30B estimate (ESTIMATED, not measured: needs the 30B download).** Per token = fixed + 48 × (GPU segment + copies
+ experts). Fixed (embedding, the same 255 MB Q6_K head, argmax, pick copy, pool wake) = the Pruned-2B's 1.348 ms per
token minus its 3 profiled layers = ~0.33 ms. GPU segment 45 µs (short) / 77 µs (8k), copies 7 µs. Experts: the 30B
reads 21.23 / 24.48 MB of r8 experts per layer (Q4_K / Q6_K down, 24 layers each; avg 22.86 MB), at the 4x0.6B's
DRAM-bound 72–76 GB/s → 317 µs, at the spec's 64 GB/s floor → 357 µs.
→ short context 18.0–20.0 ms (**50–55 tok/s**); 8k 19.6–21.5 ms (**46–51 tok/s**), vs the gate's 38. Risks: the
30B's 18 GB arena under a 30 GiB machine (RAM never measured at that size), THP coverage, and 48 pool wake-ups are
not in a 3-layer model.

## Not done / open
- (d) and (g) on the real 30B: **needs the 30B download** (18.6 GB; disk at 94%). Estimate above.
- Stage 3 (experts streamed through the GPU for long prefills): not started. Stage-2 prefill runs the experts on
  the CPU, so llama.cpp `--cpu-moe` (which offloads big-batch expert matmuls to the GPU) is faster at pp512.
- serve: works through `Lm` one request at a time (no `BatchLm` pool for the MoE); not gated here (stage 4).
- RAM: the CPU half holds only the experts (+ its r8 arena); `moe_check_ram` still counts the dense bytes too
  (conservative). The MoE scratch (~20 MB VRAM at a 1152-token pass) is inside the plan's headroom, not counted.
- The pool's workers park between tokens (the head's gap): the first layer's experts pay ~100–200 µs of wake-up
  per token (MEASURED in the profile). Small at 48 layers; not addressed.
