# Tool calls streamed as they are generated (#260)

- Date: 2026-11-14. Branch: dec/tool-stream. Base: main 0497708. Status: open
- Pick: #260 (joestar's coding-agent acceptance test, PR #235: a looping Hermes call on Qwen2.5-7B sent nothing for
  340 s, job 1113-010041-0dce). The foreman's brief: weigh (a) streaming tool-call deltas the way OpenAI and
  llama-server do, for every tool format, against (b) a bound on a held block plus SSE keepalive comments, and pick
  the one that keeps OpenAI's stream semantics. Also count unparseable Hermes blocks in `/metrics` (#259 item 3).

## What changed
- **Picked (a).** A call's head (id, name) goes out once its name has been read and its arguments open with `{`.
  Its arguments then go out as their text arrives: `delta.tool_calls` chunks on chat completions, and on Responses a
  `function_call` item with `function_call_arguments.delta` events.
- **(b) wouldn't have fixed codex.** codex's idle timer counts SSE events, not bytes:
  `codex-api/src/sse/responses.rs::process_sse_with_treatment` wraps `stream.next()` of an `eventsource()` stream
  in `timeout(idle_timeout, ...)` (:625), and comment lines dispatch no event. Argument deltas are events. codex is
  Responses-only now, and it ignores `function_call_arguments.delta`/`.done` (:569-570): it takes the call whole
  from `output_item.done` (:411). So what fixes codex is that events keep coming while a call is generated, not
  that it reads arguments early. Chat-completions clients (opencode, pi) do read the deltas as they come. The cap
  was left out: it would change the output tokens, and this PR keeps them.
- **The commit point** (`src/serve/tools/stream.rs`). `CallScan` checks a block's JSON a byte at a time with the
  grammar `parse_object_spans` uses (numbers, escapes, control bytes, the 128 depth limit). Until the commit point
  the block is held, as before, but decided early: once its text can't begin a JSON object it is content, tags and
  all. After the commit point it is a call:
  - Arguments that go bad (#259's unescaped quotes, raw newlines, bad escapes) keep streaming as written up to the
    block's end, less the object's `}`.
  - A reply cut off mid-call ends the call with what was written.
  - Both count in the new `axon_tool_calls_invalid_total`. OpenAI's API behaves the same way: `arguments` is the
    model's text, and clients check it.
  - Text after the object ends the block. A `<tool_call>` there opens the next call; other text is content.
  - An object that closes without reaching the commit point (string or array arguments, or the name after them)
    is decided whole, as before.
- **Every format.** Hermes (Qwen2.5, Qwen3) and Llama 3.1/3.2 JSON replies go through the same machine. Llama's
  `;` before another object starts the next call. For gpt-oss, `TextOut` frames a call once its arguments open
  with `{` and sends them as their tokens come. The reply still ends at the token that closes the object
  (`call_made` is unchanged). A framed call that ends any other way is a call; an unframed one is reasoning, as
  before.
- **Decide-whole mode** is main's parser and framing, unchanged. `AXON_TOOL_STREAM=0` turns it on everywhere (the
  kill switch), and the ollama routes always use it, because an ollama call is a whole object.
- **Metrics.** `axon_tool_calls_dropped_total` now also counts Hermes and Llama blocks returned as content. The new
  `axon_tool_calls_invalid_total` counts calls returned whose arguments aren't a JSON object. Both log a line with
  `AXON_SERVE_DEBUG=1`.

## How it was checked
- **Unit tests** (`serve::tools::tests::stream_*`, `call_scan_*`).
  - `call_scan_matches_the_parser`: the scan's verdict equals `parse_object_spans` on every text of `{` plus up to
    5 bytes over JSON's structural alphabet, on 4000 random objects (escapes, surrogates, every number form,
    nesting), on 8 mutations of each, and at the depth limit. A text that parses is never refused, so a refusal is
    final.
    - It has teeth: with leading zeros wrongly accepted it fails (a throwaway build, job on bella).
  - Every case runs on every 2- and 3-way split of the text, and every streamed call is checked: head, then its
    argument pieces, then its end, with the same id and the pieces joined.
    - Valid blocks give the same calls as decide-whole mode, byte for byte.
    - Each of #259's failure shapes is checked.
    - A block that never closes (`stream_runaway_block`): the head goes out with the arguments' `{`, then every byte
      as it is pushed, holding back fewer than 12 bytes (a possible `</tool_call>`). The reply's end makes the call.
      Decide-whole mode sends nothing until the end.
- **Harmony through `TextOut`** (`harmony_calls_streamed`, the gpt-oss tokenizer). The reply ends at the same
  token, with the same call. The head comes at the arguments' first token, then a piece per token. A cut-off call
  is a call, and arguments that never open with `{` are reasoning and counted as dropped.
- **Over HTTP** (`serve_tool_calls_streamed`, qwen2.5-0.5b on the CPU), both modes:
  - The same call. Streamed: at least 3 tool chunks (decide-whole mode: 2), and Responses argument deltas arrive
    after the item is added.
  - A call cut off by `max_tokens` is a call with a prefix of the arguments and finish `length`, counted invalid.
    In decide-whole mode it is content, counted dropped.
  - `serve_tool_calls` and `apis_match_chat` were updated for the cut-off call.
- **End to end** (`tool260.py`): main, the candidate, and the candidate with `AXON_TOOL_STREAM=0`, greedy, on
  Qwen2.5-7B, Qwen3-8B, Llama-3.2-3B and gpt-oss-20b. 10 tool requests each (chat and Responses, whole and
  streamed).
  - The same tokens in every arm.
  - The kill switch is main's output, event for event.
  - Where main made calls, the candidate makes the same ones.
  - Where it didn't, the candidate's calls are text from main's content.
  - Streamed replies fold to the whole ones.
- **End to end: the rule, amended in the open.** tool260's pre-registered `same-tokens` check was "every arm the
  same `completion_tokens` and finish". 1114-071452-6ca3 (code 2bb37d3, pod1 4090) failed it on one request, on two
  models: `auto-json-in-shell`, Qwen2.5-7B base `(50, stop)` against cand `(50, tool_calls)`, Llama-3.2-3B
  `(18, stop)` against `(18, tool_calls)`. Qwen3-8B passed; `off == base` held on all three. The counts are equal.
  The finish differs because the candidate returns #259's broken shell call (`"echo \'…"`, an invalid escape;
  Llama's `"echo \\""`) as a call, the declared policy change, and a call has finish `tool_calls` on chat. The rule
  contradicted the PR's own spec, so it was amended rather than waved through (shady's MUST 1):
  - **The amended rule** (the foreman signed off, as maintainer, on 11-14): tokens identical; finish may go `stop`
    → `tool_calls` only on a request the job lists as a policy change.
  - The API exposes no token ids, so "tokens identical" is checked as the same `completion_tokens` in every arm plus
    byte-identical decoded text. `off` equals `base`, reply for reply. On each policy request, `base`'s text is
    rebuilt exactly from `cand`'s: `base` content = `cand` content + each call's raw block (`<tool_call>` /
    `<|python_tag|>`, `{"name": N, "arguments"|"parameters": ` ARGS `}`, the closer optional when cut off), or for
    harmony `base` reasoning = `cand` reasoning + the arguments. This replaces the old substring test ("cand's
    arguments appear in base's content"). The 6ca3 replies show it: Qwen2.5-7B's base content is exactly
    `<tool_call>\n{"name": "exec_command", "arguments": ` + cand's arguments + `}\n</tool_call>`.
  - The engine is untouched (no engine or model file in the diff; `stream_calls` reaches only `TextOut`, after
    decoding), so tokens can't move by construction; the check is the evidence that they didn't.
  - 6ca3's saved replies, fetched from pod1 and re-judged with the amended rule: PASS on all three models. The
    judge can fail: on planted mutations of those replies (one word of the block, a token count +1, a finish flip
    on a non-policy request, `stop` → `length` on the policy request, text after the block, the wrong call name) it
    failed 11 of 11. The twelfth plant, a finish flip on Llama's `auto-text`, changed nothing: that reply is
    already a call.
  - Rerun with the amended script, code 2bb37d3: 1114-072714-5102 (pod1) PASS on all three models.

## Review round (shady 8/10 SHIP, Fable second-family 8/10 APPROVE; neither had a MUST on the code)
- **The block's own `</tool_call>` after junk is dropped** (shady SHOULD 1, Fable SHOULD 2). Text after a call's
  object ends its block without the tag; the tag, if it comes later, used to show in `content`, while junk *inside*
  the object already dropped it. Now the first `</tool_call>` before the next `<tool_call>` is dropped (`stray`),
  and text that may begin either tag waits, so it holds on every split. Tests: `stream_hermes_*` (first only, a
  `<tool_call>` first, a tag cut short at the end).
- **Streamed or not, said plainly** (shady SHOULD 2): `serving.md`, `environment.md` and the CHANGELOG say a
  `"stream": false` reply decides calls the same way (bad arguments come back as a call there too).
- **Responses: a cut call is `incomplete`** (shady SHOULD 3, Fable SHOULD 1). The rule, the same in `whole()` and
  the stream: if the response's last item is a call whose arguments aren't a JSON object, and the response is
  `incomplete` (the token limit), that item is `incomplete`; any other call is `completed`. The stream holds such a
  call's `.done` until the next item opens or the reply ends. This matters to codex: on `response.incomplete` it
  raises `ResponseIncomplete`, whose `partial_output` keeps only items with status `incomplete` (`:476-512`). Test:
  `serve_tool_calls_streamed` (whole and streamed agree, both modes).
- **`</tool_call>` inside a JSON string in a call's arguments is the string's text** (Fable SHOULD 3). It used to cut
  a committed call there, though the scanner knew it was inside a string. Now, while a committed call's
  arguments are still JSON and the scan is inside a string with no escape begun, the tag goes in as argument bytes.
  Raw (arguments gone bad), the name, and after the arguments keep the old cut.
  - shady warned (for constrained decoding's PR B) that without a grammar an unterminated string could swallow the
    rest. In Hermes output it can't: the model writes a newline before `</tool_call>`, a raw newline is a byte no
    JSON string holds, so an open string goes bad (Raw) there and the tag still ends the block. A test pins that
    case. Only a model that writes the tag straight after an open string, with no newline, loses the block's end
    to the string; the call is then invalid either way. PR B keeps this order (scan first, tag second).
- **gpt-oss: framing and `call_made` agree on text before the `{`** (Fable SHOULD 4). `ArgScan` (main's) skips any
  non-ASCII byte before the `{`; `call_made` parses `args.trim()`. A call with `é` first was framed from the `{`,
  then refused, and ran on to `<|call|>` as a call. Now `call_stream` frames only when what precedes the `{` is
  blanks `trim` drops. Such a call (U+3000 first) is made, streamed or not. Any other (`é` first) is never framed
  and never made: reasoning, as in decide-whole mode. `ArgScan` is unchanged, so decide-whole mode is still
  main's. Test: `harmony_calls_streamed`.
- Docs also take Fable's nits: the kill switch is exactly `0`, and a stop string inside a call's arguments ends it
  with `finish_reason: "tool_calls"`.
- Left for after merge: shady's SHOULD 4, a codex rerun of #235's acceptance arm on the candidate (joestar). The
  other nits (an empty `"name"`, O(n²) whitespace in Raw's held tail, a no-op event for silent stretches, the
  no-commit shapes) go to the follow-up issue.
