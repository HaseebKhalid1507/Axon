# Dense CPU loads refused when they can't fit in the RAM available  (PR #142)

- Date: 2026-10-26. Branch: fix/ramdense. Base: main 39624db, merged up to 161e787 (docs only). Status: open
- Pick / design: issue #135 (follow-up of #133 / #129). Follow-up filed: #143 (the CPU half of a `--gpu-layers` split).

## What changed
- `model::check_ram_dense` runs for every dense model built for the CPU (`Backend::new_capped`, next to the MoE
  `moe_check_ram`). It refuses (exit 2 through the CLI) when what the load commits, plus the KV cache of
  min(ctx, 8192) positions, exceeds `gguf::mem::avail()`: the host's `MemAvailable`, or the room under the tightest
  cgroup limit (#133). The message names the bound. It is worded as the MoE one, both now in GiB:
  `qwen2: the CPU model needs about 0.37 GiB of RAM (its repacked weights 0.37 GiB, the KV cache of 14 tokens
  0.00 GiB) and only 0.26 GiB is available (bound by cgroup /…/x.scope memory.max 320 MiB)`.
- **What the load commits** (`dense_load_bytes`):
  - Mapped file (the default for a model that repacks): the whole r8 arena. `dense_ram_need` lays it out as
    `Qwen2::build` does (the output head plus the shared `DENSE_MATS` list, layers below the block count, 64-byte
    offsets, 2 MB pages). The file's pages are page cache the kernel reclaims, so they aren't counted (#128).
  - Copied (AXON_MMAP=0, or a model that reads some matrices in place): the copy is already in use at the check.
    `build` repacks the head first, alone, then the layers a matrix per pool thread, and hands each repacked matrix's
    copied bytes back right after (`Weight::load`), except a tied head (the embedding reads it). So the peak adds
    the growth (repacked minus replaced bytes), a tied head, and the larger of an untied head and
    threads × (largest layer matrix + 4 MiB of release granularity), capped at the arena.
- **KV:** the CPU cache is a lazy mapping (`KvBuf::zeroed`: pages taken as the context fills). So only the KV of the
  first min(ctx, 8192) positions is refused on. A full explicit `--ctx` cache that wouldn't fit prints a note (the run
  is OOM-killed if its context fills) and loads. No note when the context is left to fit (serve's `cpu_ctx` sizes it
  to the RAM).
- MoE's refusal messages: GiB instead of decimal GB; cgroup limits are printed in MiB (they were MiB labelled MB).
  MoE keeps its 1.5 GiB headroom; why it differs from the dense check's none is written at `RAM_HEADROOM`.
- README (CPU memory limits) and CHANGELOG lines.

## Why
#135 / job 1025-054259-1d9c: qwen2.5-0.5b `gen --device cpu` under `MemoryMax=400M` was OOM-killed (rc 137) on main.
Only MoE models had a RAM refusal. Containers and systemd scopes run under memory limits, and an OOM kill gives the
operator nothing to act on.

## What didn't work
- **32 MiB of headroom** on top of arena + KV (b6f88df): job 1025-224358-e406 refused all six models at exactly the
  smallest cap main runs at, each 10–20 MiB short. Dropped: no headroom. The price is a band of tens of MiB above the
  committed bytes (the forward pass's scratch, the process) where a load is still OOM-killed, not refused.
- **Counting the full KV of an explicit `--ctx`, and the whole arena for a copy** (a82b927, review round 1): both
  over-count. The KV is lazy, and a copy hands repacked bytes back as it goes. They would refuse loads that run on
  main (e.g. `chat --ctx 131072` on an 8B, or a Q4_K_M under AXON_MMAP=0 at about 55 % of the cap).
