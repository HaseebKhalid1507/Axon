# MoE stages 0–1: qwen3moe loads, `axon info`, CPU-only forward  (PR #TBD)

- Date: 2026-10-17. Branch: feat/moe. Base: main cf68e9d. Status: open
- Pick / design: r11 MoE spec (`specs/r11-moe.md`, forum "r11: MoE design"), stages 0 and 1. Roadmap Scale item 7.

## What changed
- **Stage 0.** `qwen3moe` joins `ARCHS`. `check_supported` reads `expert_count`, `expert_used_count`,
  `expert_feed_forward_length` and checks `ffn_gate_inp` (F32/F16 `[dim, n_expert]`) and the 3-D
  `ffn_{gate,up}_exps` `[dim, ffn, n_expert]` / `ffn_down_exps` `[ffn, dim, n_expert]`. Refused: shared experts
  (count or `*_shexp` tensors), `expert_weights_scale` ∉ {0, 1}, a gating function other than softmax,
  grouped selection, `expert_weights_norm` false, `expert_used_count > expert_count`, a dense `ffn_gate` in a MoE
  file, `exp_probs_b`. Experts on any other arch: still refused. `axon info` prints experts, top-k, expert ffn,
  expert bytes (file and r8), active bytes per token and non-expert bytes. `--device cuda`, a split or a pipeline
  refuse with "qwen3moe: mixture-of-experts models run on the CPU only for now (--device cpu) ..."
  (`Backend::new_capped` before opening the GPU; `CudaQwen2::plan` for every other GPU entry, e.g. a draft
  model), and identity's cuda fingerprint says so. A MoE file is always mapped, never copied
  (`reads_matrices_in_place` is false for it, `AXON_REPACK=0` included): a copy beside the r8 arena would hold
  the experts twice.
- **Stage 1** (`src/model/moe.rs`). A layer's FFN is `Ffn::Dense{gate,up,down}` or `Ffn::Moe(Moe)`. Each expert
  matrix (a slice of the 3-D tensor) is its own `Weight`: repacked into the r8/r8q arena (contiguous per expert
  matrix; the tensor's pages released once all its experts are repacked) or read in place with `AXON_REPACK=0`.
  - Router (`Moe::route`, per token, same code for decode and batches): logits accumulated over the input in
    ascending order, multiply then add (vectorized across experts on a transposed copy: same bits), softmax with
    `vmath::exp_f` (sum ascending, divide), exact top-k by `(p desc, index asc)`, weights `w_i / s` with
    `s = max(Σ w, 6.103515625e-5)` (llama.cpp CPU's division and clamp).
  - Decode (`moe_ffn`): 2 pool fork/joins per layer. A: gate+up rows of the k experts + SwiGLU (chunks never
    straddle two experts). B: per output-row chunk, the k experts' down rows in rank order, summed
    `y = w_0 d_0; y = y + w_i d_i` as they come. No cross-thread reduction.
  - Batch (`moe_ffn_batch`, prefill and verify): counting sort of the (token, slot) pairs by expert (ascending
    pair order), then per (expert, row chunk) `r8::gemm` over that expert's tokens (bit-equal to `gemv` per
    token), down the same way, then a pass over (row, token) doing the same rank-order sum. Sub-batches of 512
    tokens bound the scratch; bits don't depend on it.
  - Load-time RAM check: the CPU backend refuses a MoE model whose repacked weights + 1.5 GiB exceed
    `MemAvailable`.
- `axon logits` honours `AXON_LOGITS_DIGITS` (more decimals for scripts). `scripts/oracle/llama_logits.py`:
  next-token top-K from `axon logits` and from llama-server (same token ids), and top-1 / KL comparison.
- Seams for stages 2–3: `Ffn` is the enum the GPU `LayerW` will mirror; `Moe::route` is the CPU twin of the
  planned `moe_route` kernel; `host_layer` stays dense-only (`Layer::dense()` panics on a MoE layer, and the
  hybrid never sees one: `CudaQwen2::plan` refuses first); experts are `Weight`s, so a streamer can treat each
  as a `HostMat{repacked: true}`.

## Why
Spec r11 stage 0/1: a CPU-exact MoE path first, graded against llama.cpp, before the GPU split. Dev models:
`Qwen3-30B-A3B-Instruct-Pruned-2B.Q4_K_M` (3 layers with the 30B's exact shapes and type mix: 128 experts,
top-8, ffn 768, Q6_K down in layer 2) and `Qwen3-MOE-4x0.6B-2.4B-Writing-Thunder-V1.2.Q4_K_M` (4 experts, top-2,
28 layers, coherent text). The full 30B was not downloaded (disk).
