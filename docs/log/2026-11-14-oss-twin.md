# gpt-oss experts on the GPU, stages 0 and A: the measurements, and the MXFP4 twin kernels  (PR #271)

- Date: 2026-11-14. Branch: feat/oss-twin. Base: main 9f3630c. Status: draft (PR #271).
- Pick / design: specs/gptoss-gpu-experts.md (overnight workspace; Fable), the roadmap's weeks 2–3 item: stage 0
  (measure) and stage A (the MXFP4 twins). Review: specs/gptoss-gpu-experts.review-shady.md (7/10; MUST 1, the exact
  i32 → f32 conversion by the magic-number seed, is in the kernels; MUST 2, the foreman's stop rule, is applied in
  "Projected ratio" below).

## What changed
- **Stage 0 (94b6f09).** `AXON_MOE_PROFILE=1` now reports every batched pass of the split (attention on the GPU,
  experts on the CPU) per layer: the GPU segment (synced), the copy down, unpacking, the CPU experts, the copy up, then
  the pass's wall time and the experts' share. Before this it reported decode steps only. Nothing changes without the
  variable. `src/moe/oss_s0_tests.rs` (ignored; measurements only): `oss_s0_h2d` (one layer's experts host to device
  by three paths) and `oss_s0_vram` (the GPU half at ctx 8192 / 32768 and what is left for expert layers). The
  profiler extension ships in this PR (PR B and C measure with it), not a throwaway branch.
- **Stage A (d78a84f), all in `src/cuda/oss.cu`** (the gpt-oss module, `KERNELS_OSS`; no other module's source
  changes):
  - `mx_repack`: the file's 17-byte MXFP4 blocks into an aligned layout at upload (16 code bytes per block with rows
    16-aligned, the scale bytes apart). Same bits, nothing recomputed.
  - `moe_gemm_mx` (the grouped GEMM of the batched path), `moe_gemv_mx` and `moe_gu_mx` (decode; gate and up in one
    launch). Each output is `quant::dot_row_q8` of mxfp4.rs: per block and per lane l (values 4l..4l+3) an exact i32
    sum by `dp4a` (E2M1 codes to their doubled integers by `__byte_perm` lookups, llama.cpp's
    `get_int_from_table_16`; |sum| ≤ 4 × 12 × 128), converted to f32 exactly by seeding the accumulator with
    0x4B400000 and subtracting 12582912.0f (review MUST 1; `gm_i2f`'s trick), `acc[l] = fma(e8m0_half(e) * dx,
    lane, acc[l])` with the block loop ascending, then `hsum8`'s tree ((l0+l4)+(l2+l6))+((l1+l5)+(l3+l7)), then the
    bias added (`__fadd_rn`).
  - `swiglu_oai_twin`: vmath.rs `swiglu_oai1_f::<F>` (alpha 1.702, limit 7, `exp_twin`). `x = fminf(g, 7)` (NaN g
    gives 7, as `f32::min`); `y` clamped by comparisons, so a NaN u stays NaN as `f32::clamp` keeps it (fminf / fmaxf
    would give -7; review SHOULD). Fused with the Q8 quantization of its output for the down GEMM
    (`swiglu_oai_quant_tw`).
  - `CudaExperts` (experts.rs) uploads MXFP4 experts with their three bias vectors; the decode path and the batched
    path dispatch on the type. Product code doesn't reach it yet: `place_resident` still refuses gpt-oss (stage B
    lifts it), so no model runs differently.
- **Tests** (`src/cuda/qwen2/oss_twin_tests.rs`): `oss_twin_dot_matches_cpu` (moe_gemm_mx and moe_gemv_mx vs
  `dot_row_q8`, every output's bits; teeth: a sequential lane sum differs), `oss_twin_swiglu_matches_cpu` (1.25 M
  values incl. ±7 edges, NaN, ±inf, both F; teeth: plain SwiGLU and the NaN-blind clamp differ),
  `cuda_experts_oss_fixture_match_cpu` (a 3-layer fixture with biases: whole layers at nb 1, 7, 48, 129, 1152 vs the
  CPU's `moe_layer_batch`), `cuda_experts_oss_match_cpu` (the real model's layers 0, 1, 12, 23, same nbs),
  `cuda_experts_oss_bench` (ignored; the speed gate).

The kernel rate the 0.8× and 0.9× bars need (foreman's MUST 2): a pp512 pass is 1,223 G expert MACs
(24 layers × top-4 × 3 matrices × 2880 × 2880 × 512). With T_ne = 22 ms, 0.8× of 12,171 (52.6 ms a pass) leaves

the whole expert layer (quantize, sort, gather, 3 GEMMs, activation, sum), not the GEMM alone, and they sit at 75 % /
93 % of the review's ~53 T issue ceiling for a dp4a twin. If T_ne were 12 ms they would be 30 / 35 T: the 4090 bar
also depends on Axon's non-expert time.

re-measure of bella's 265 / 46.6 at 9f3630c. They are PR C's inputs; nothing in A depends on them.

## Projected ratio (the foreman's stop rule)
**DERIVED, not measured** (no all-resident gpt-oss path exists until stage B; no more pod runs). A pp512 pass on the
4090 with every expert resident ≈ T_ne + 24 × the layer at nb 512:
- T_ne (non-expert GPU time of a pass, stage 0's profile at nb 510) = GPU segments 29.80 ms − y's uploads
  (23–24 × 5.9 MB at 13.34 GB/s = 10.1–10.6 ms, which go away) + rest 2.52 ms = **21.75–22.19 ms**.
- Layer at nb 512 = **2.343 ms** (1fd0), × 24 = 56.2 ms.
- Pass 78.0–78.4 ms ⇒ **pp512 ≈ 6,530–6,570 tok/s = 0.536–0.539× llama.cpp's 12,171**. That's inside the spec's
  pre-registered 5,500–10,000, below the 0.8× line.

What the bars need: 0.8× leaves 30.6 ms of experts a pass, a layer in 1.274 ms (40.0 T MAC/s, **1.84×** today's);
0.9× leaves 24.7 ms, 1.031 ms a layer (49.4 T, **2.27×**). The layer's 2.343 ms wasn't split between its three
GEMMs and the rest (sort, gather, quantize, activation, sum). If its GEMMs took 0.65–0.72 ms each (between the standalone
uniform and random-routing times, as far as the total allows), the rest is 0.18–0.39 ms. Then even GEMMs at the review's ~53 T issue ceiling (16.99 G MAC in 0.32 ms each)
give a layer of 1.14–1.35 ms, **0.77–0.85×**. So 0.8× needs the dp4a twin at or near its issue ceiling, which real
kernels don't reach, and 0.9× is out of reach even there (1.14 > 1.031 ms). Either bar would need the spec's §3
escalations (U, or E2's int8 `mma.sync` on requantized weights; the maintainer's call) or a smaller T_ne. Per the foreman's
ruling, no tuning time went into chasing it. The twin is still stage B/C's base on bella (the 3× bar), where the spec
expects PCIe, not the kernel, to set the pace (bella's stage 0 rows are still to be measured).

## What didn't work / notes
- jade (GTX 1060, sm_61) is out of scope for performance. The twin kernels run there (dp4a is sm_61+), so its
  correctness runs are free; `CudaExperts::layer`'s batched path refuses sm < 80 as for every twin type, and the
  tests take the decode path there.
- The first jade run (1114-201656-ad71) failed `cuda_experts_oss_fixture_match_cpu` with that refusal, not with a bit
  difference: the test called the batched path after its nb sweep. It now calls the decode path there.
- The first pod run of A (1114-202853-0d34) failed on two test bugs, not on bits. The bench's whole-layer part drew
  expert ids as `(u64 >> 20) as i32 % 32`, negative for half the draws, so `CudaExperts::check` refused them (fixed
  in c369128). `cuda_experts_oss_match_cpu` built its CPU reference with `new_experts_of`, which is deepseek2-only
  (fixed in a07e02f: `new_experts_except`). The rerun, 1fd0, is the record.
- Pod spend for stages 0 and A: $0.224 (stage 0) + $0.209 + $0.179 (A's two runs) = $0.61, about 38 pod-minutes.
