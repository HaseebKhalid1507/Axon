# 2026-11-04 fp8-sm89: the e4m3 product step on sm_89 is two f16 mmas (#190)

Branch `fix/fp8-sm89`, off main 330146b.

## What failed and why
`gpu_fp8_gemm_bits_and_anchor` fails on a 4090 every time, in release and debug at main af281d9 (1104-193717-bce3,
1104-193717-89a8, 1104-191235-2023):
`gemm_ref_f8 k 128 rows 64 nb 17: output 0: -0.31081602 vs exact -0.3107885997747955`. The bits check passes:
`gemm_f8` and `gemm_ref_f8` agree. Only the f64 anchor fails, and it fails for both kernels. The raw accumulator
is −155408 where the exact sum of the products is −155394.285. One step of the e4m3 `mma.sync` on sm_89 cuts its
terms, the incoming accumulator among them, about 13 bits below the largest (multiples of 16 here). That rule gives
−155408 exactly. It is the narrow in-mma accumulator the design's §3 anchor was written for. A model search over
alignment width, step size and rounding direction found no rule that matches every output bit for bit, so the
rule is a description, not a spec.

**Correction to #190:** the §3 kernel checks never ran on an H100 or on any sm_89 GPU before this. Their 16
passing runs are all on bella (sm_120). The #177 log already lists "sm_89 runs of the graded gate and the kernel
checks" as not run. `gpu_fp8_graded_vs_fp8_ref` reported ok on the 4090 in 1104-191235-2023 because it skipped:
the pod had no FP8 checkpoint (`testutil::fp8_model_path`). Main 0e014cd's postmerge shards on a 4090 pod
(1104-212923-c2b0, -db5f) reported it ok the same way: that pod had no checkpoint either (1105-004038-45de found it
absent and fetched it). Filed as #193: since its fix, a missing checkpoint fails these tests instead.

## Diagnosis (`gpu_fp8_mma_diag`, ignored, by hand)
Worst error at the §3 shapes, relative to the tolerance, at K 128 / 896 / 4864:

| path | 4090 sm_89 (1104-195209-4f1e) | bella sm_120 (1104-194742-ccb2) |
|---|---|---|
| e4m3 chain (main) | 173× / 114× / 36× | 0.062× / 0.078× / 0.050× |
| promoted into f32 every 4 mmas (128 K) | 173× / 32× / 4.0× | 0.062× / 0.018× / 0.005× |
| promoted into f32 after every mma | 67.6× / 13× / 1.7× | 0.039× / 0.023× / 0.006× |
| f16 codes, two m16n8k16 f16 → f32 mmas per k32 | 0.124× / 0.176× / 0.131× | 0.089× / 0.120× / 0.095× |

Promotion every mma still misses by 67.6× at K 128, because the cut happens inside the instruction. That rules out
the design's planned `AXON_F8_PROMOTE`. The tolerance model wasn't changed. It is right: sm_120's e4m3 chain clears it
with 12.8× to spare (worst 0.078×). On the 4090, 174943 of the 201792 sampled outputs miss it, with errors up to 9.2e-4 of ws·das·Σ|w·a|
(the f16 path: 3.0e-6). That is a real loss of precision, not slack in the bound.

## Fix
`mma_f8` (`fp8.cu`): compile targets sm_120 and later keep the e4m3 `mma.sync`, so the sm_12x cubin's code is
unchanged. Every older target (sm_89, 90, 100, ...) converts each fragment register to f16x2 (`cvt.rn.f16x2.e4m3x2`, exact) and run two `m16n8k16` f16
mmas with f32 accumulate on the same fragments. `gemm_f8` and `gemm_ref_f8` share `mma_f8`, so the bits check
compares the same thing as before. `-DAXON_F8_E4M3_ACC` forces the e4m3 mma, which tests use to time it.
The `#if` keys on the compile target, not the card: an sm_120 card whose NVRTC lacks sm_120 would get older PTX and
the f16 path (correct, slower; `code_target` is in the identity). `nvrtc_fp8_product_step_by_target` (NVRTC only, no
GPU) checks the routing: the e4m3 mma is in the PTX at compute_120 and nowhere at 89, 90 or 100.

`NUMERICS_VERSION_FAST` goes 2 → 3 (f898762): this changes fast-mode bits below sm_120, and identity.rs's rule
bumps the fast counter for that (shady's review; [lead ruling](https://github.com/HaseebKhalid1507/Axon/pull/191#issuecomment-6651890843): no waiver, and fast sessions saved on sm_120
restoring once as tokens is accepted). It is a later commit than the kernel
change (1589821) because that one was pushed already.

On the 0.5B, FP8 fast-mode prefill on sm_89 is 17–22 % slower (MEASURED). Decode doesn't change, because it runs
`gemv_f8`, not the GEMM. The 7B is not measured. At its shapes the GEMM alone is 1.32–1.42× (the table above), 24–30 %

collects the ideas for winning it back. Per-mma promotion of the e4m3 mma is already measured there: it misses the
anchor by 67.6× / 12.6× / 1.73× (4f1e's P1 path).

## The graded gate's decode arm on sm_89 (#192)
With the checkpoint on the 4090, `gpu_fp8_graded_vs_fp8_ref` failed on its decode arm and nothing else, the same way
on main af281d9 (1104-195957-7b43) and on this branch (1104-195956-a644): 926/1014 top-1, 12 flips at a reference
margin >= 0.5 against the order-only allowance max(2, n / 100) = 10. The CPU floor alone flips 10 such margins and bella
flips 8. Every other bound put the 4090 at the floor. A cross-GPU comparison of teacher-forced decode logits (933
positions, `logx.sh`; 4090 1104-212053-2aeb, bella 1104-212054-8064) places the difference in shared code:

- With no FP8 kernel in the step (Q4_K_M, or the FP8 model in exact mode), sm_89 and sm_120 differ at 931-932 of 933
  positions, top-5 |dlogit| mean 0.07-0.08.
- Fast mode differs by 0.197 on average, about 2.5× that. Its kernels `gemv_f8` and `quant_f8_tok` match their CPU
  references bit for bit on both GPUs, so they amplify the shared difference through e4m3 rounding but don't start it.

Lead ruling ([#192](https://github.com/HaseebKhalid1507/Axon/issues/192#issuecomment-6648003748)): for
`Top1::Binomial` only, the count becomes max(2, n / 100, w_f + 2 sqrt(n p (1 - p))), with w_f the floor's count and
p = w_f / n. That is 16 here. Built in 08f37f4, with the unit test `wide_flips_rule`. The order-only gates are unchanged. 12 ≤ 16 above is
arithmetic on a644's counts. The run at 023a37a is 1105-004038-45de (a second 4090 pod, the checkpoint fetched and its
sha256 checked). It passed every arm, with the same counts as a644: decode 926/1014 and 12 wide flips, within 16. It
printed the `note:` line. The kernel code is unchanged since 1589821, and every arm's printed numbers match a644's
from the first pod exactly.
