# gpt-oss stage 0: MXFP4, the openai-moe graph, o200k, harmony (CPU only, exact)

2026-10-18. Branch `feat/gpt-oss` (stacked on #67, now merged; based on main).

## Why

The mission is "inference cheap and fast, and it has to run the best models". gpt-oss-20b is one of the
most-used open models and the roadmap's MoE item after Qwen3-30B-A3B ("gpt-oss-20b (MXFP4, sinks) after").
Stage 0 gets it running on the CPU, exactly (Axon's decode == batched prefill == verify contract), with
logits inside llama.cpp's own CPU/CUDA spread. The GPU comes in stage 1 (plan at the end).

## The file

`ggml-org/gpt-oss-20b-GGUF`, `gpt-oss-20b-MXFP4.gguf`, 12 109 566 624 bytes, sha256
`27cd6c432c7672cb812a92f611cf3ba7bbc35928262bb1e1253ff4ee6ae35901`. 24 layers, dim 2880, 64 query heads /
8 kv heads of 64, 32 experts top-4 of ffn 2880, window 128, YaRN factor 32 over 4096 (base 150000),
vocab 201088. Types (inspected): attention q/k/v/o, embedding and output head Q8_0; norms, biases, sinks
and the router F32; the 72 expert tensors MXFP4. `axon info`: experts 10.15 GB, active per token 1.27 GB,
non-expert 1.94 GB.

## What changed

- **MXFP4** (`src/quant/mxfp4.rs`, ggml type 39): 17-byte blocks (E8M0 scale, 16 bytes of E2M1 codes).
  Dequant is llama.cpp's `dequantize_row_mxfp4` bit for bit (`e8m0_half` reproduces
  `GGML_E8M0_TO_FP32_HALF`, subnormal cases included). Checked against llama.cpp's own type traits by a
  scratch C tool (`mxdq`, linked to llama.cpp 4413a19's libggml): FNV-1a of every exponent x every code
  byte, and of two whole expert tensors of the real file (`dequant_matches_llama_cpp_*`).
  Dot against Q8_0 activations: per block 8 exact i32 lanes (AVX2 maddubs/madd or AVX-VNNI dpbusd, sign
  trick), `acc[l] = fma(e8m0_half(e) * dx, lane, acc[l])`, then the 8 lanes in the AVX2 horizontal-sum
  order. The scalar kernel does exactly that (`f32::mul_add`), so scalar == AVX2 == VNNI, for one row,
  decode rows (4 at a time, prefetch), 4 tokens, and pairs (`every_path_same_bits`). Layout: the file's;
  the experts are read in place from the mapping (no repack, no copy), so a GPU upload is the same bytes
  llama.cpp's CUDA kernels take.
- **The graph** (`src/model.rs`, `src/model/moe.rs`; llama.cpp `src/models/openai-moe.cpp`): qwen2's qkv
  biases plus the attention output bias; per-head **sinks** (`vmath::softmax_sink`: the max and the
  normalizer include `sink`, which has no value row, as `soft_max_ext`); **sliding window** 128 on the even
  layers (`load_swa_pattern(ml, 2)`; gemma3's machinery, generalized: the local layers keep a full-length
  cache and attend to `[pos-127, pos]`); **YaRN** from the GGUF on every layer (local ones too, as llama.cpp's
  `freq_base_swa = freq_base`, `freq_scale_swa = freq_scale`); the pre-FFN norm is the file's
  `post_attention_norm`. MoE (`Oai`): router logits + bias, the top 4 on the logits, their weights the
  softmax over those 4 (`SOFTMAX_WEIGHT`, no renorm: softmax-all-then-renormalize is the same thing), each
  expert's gate/up/down + its bias, and `swiglu_oai` (x = min(g, 7), y = clamp(u, -7, 7),
  x * sigmoid(1.702 x) * (y + 1)). Decode and the batched path run the same ops in the same order per
  (row, token), so the contract holds.
- **Tokenizer** (`src/tokenizer.rs`): `Pre::Gpt4o`. llama.cpp runs o200k's regex through std::regex on
  "collapsed" text (every non-ASCII letter one stand-in byte), after rewriting `[\p{Lu}...]` as
  `((?=[\p{L}])([^a-z]))`: so its "upper" is any letter but a-z and "lower" any letter but A-Z. The regex
  here says exactly that (`[\p{L}--a-z]`, `[\p{L}--A-Z]`). No BOS. End of generation: `<|return|>`,
  `<|call|>` (not `<|end|>`, as llama.cpp's harmony workaround).
- **Harmony chat** (`src/chat.rs`): `Format::Harmony`, the GGUF template without tools, a fixed date
  (`HARMONY_DATE`, so a conversation's tokens don't depend on the day), reasoning medium; the system
  message goes in a `developer` block (`# Instructions`). A reply is generated after `<|start|>assistant`;
  `<|end|>` is not a stop. When a reply closes, the history keeps its last channel only
  (`<|channel|>final<|message|>...<|end|>`, the template's rendering of earlier turns) and the next turn
  re-feeds from there (as Qwen3's `</think>` cut). `Channels` splits a reply as it streams: `axon chat`
  shows the final channel only (and notes "reasoning N tok, not shown"); `axon serve` returns the
  analysis channel as `reasoning_content` and the final channel as `content` (`--think-inline`: the raw
  stream, markers included, in `content`). Tools are not offered for harmony yet (the tool families stay
  Qwen and Llama 3).
- **Placement** (`src/lm.rs`, `src/model/moe.rs`): `--device cuda` refuses gpt-oss with a pointer to
  `--device cpu` (stage 1). The file is mapped (never copied: a 12 GB anonymous copy on a 30 GB box is
  how bella ran out of memory once), and the expert tensors' page tables are filled at load
  (MADV_POPULATE_READ: no fault per 4 KB on the first tokens, no extra memory). `check_ram` counts only
  what goes into the anonymous arena (the experts' share is 0 here).

## How it was verified

Host: bella (Intel Core Ultra 9 275HX, 8 P + 16 E cores, 30 GB RAM, AVX2 + AVX-VNNI, no AVX-512), every model
run through `axon-run --cpu` (axon-q CPU slots are 8 E-cores: 8-15 or 16-23). llama.cpp 4413a19 (`build/` CPU,
`build-cuda/` CUDA 12.8). Scratch tooling in `~/.cache/axon-gptoss` (oracle.py, tfcmp.py, ref/mxdq.c).

**MXFP4.** `dequant_matches_llama_cpp_bits` (every e x every code byte) and `..._on_gpt_oss` (blk.0
ffn_down_exps, blk.23 ffn_gate_exps, 8.3 M blocks each): FNV-1a equal to llama.cpp's type traits. PASS.
`every_path_same_bits`: scalar == AVX2 == VNNI on every entry point, and the scalar kernel within 1e-5
(relative to Σ|w x|) of the f64 dot. PASS.

**The graph vs an independent f64 reference** (`gpt_oss_matches_reference_forward`, a 3-layer fixture with
MXFP4 experts, window 4, YaRN factor 4, sinks, every bias): max |dlogit| 0.32 (one position where two experts
nearly tie under 8-bit activations; the other 23 <= 0.19), logits ~2-3. Each deliberate bug moves them far
more: no sinks 3.8, no window 5.4, no router bias 1.0. (Softmax-over-all-then-renormalize was a planned
bug: it is the same as softmax over the k, so it can't be told apart and isn't one.) PASS.

**vs llama.cpp** (20 prompts x 64 greedy tokens, `oracle/oss-{cpu,cuda}.json`; jobs 1018-004504-d79d CPU,
1018-004504-7a6f CUDA with `--n-cpu-moe 10`, since 12.1 GB doesn't fit bella's 12 GB card: layers 0-9's
experts ran on llama.cpp's CPU kernels). Axon CPU teacher-forced on each trajectory
(`teacher_forced_dump`, job 1018-015032-3876):

|---|---|---|---|
| llama.cpp CPU vs llama.cpp CUDA (their common greedy prefix) | 1025/1031 (99.4%) | | 0.0030 / 0.100 / 0.358 |
| Axon CPU vs llama.cpp CPU (teacher-forced, all positions) | 1262/1274 (99.1%) | 12/12 | 0.0033 / 0.085 / 0.430 |

the rest 56/58-63/64, every miss a near tie. llama.cpp's own greedy CPU and CUDA runs are identical on 14/20.

**Tokenizer** (`oracle_gptoss`, `tests/fixtures/tokens_gptoss.json`, 40 texts: code in four languages,
numbers and dates, whitespace runs, CRLF, eleven scripts, emoji/ZWJ, math, nbsp/ideographic space,
contractions in both cases, CamelCase): token for token == llama.cpp, plain and special-parsed; the 20
prompts too. One deliberate difference: llama.cpp marks `<|start|>`, `<|message|>`, `<|channel|>`,
`<|constrain|>` and `<|end|>` USER_DEFINED for this vocabulary ("quick hack for gpt-oss",
llama-vocab.cpp), so its *plain-text* tokenizing turns those strings into control tokens. Axon's never does
(user text can't forge a turn, as for every other format); `encode_special` matches llama.cpp.

**Harmony** (`harmony_framing_and_channels`): the framing == the GGUF template's text (system defaults,
`# Instructions` developer block, earlier assistant turns as `final`, `<|start|>assistant`), and the stream
split (analysis -> reasoning, final -> answer, markers hidden). Sample, `axon chat --temp 0`, two turns

**Contract.** `gpt_oss_decode_batch_verify_bits` (fixture, repack on and off) and `gpt_oss_model_bits` (the
real model): decode == `feed_batch` over every batch size 1..9, 13, 17, 64, 86, 128, 130 (483 tokens, past
the window), bit for bit in every layer's K/V and the logits; `verify_batch` == `forward` per position;
`verify_argmax` == greedy; a cache built as prefix + rest == one fresh prefill (KV bits and logits). PASS
(job 1018-015032-3876; `AXON_SIMD=scalar` rerun: job 1018-020932-717d).

**No change to other models.** md5 of `gen` output, base (main a032773) vs candidate, same host, same run
(job 1018-014124-3f4d): 9 models (Qwen2.5 0.5B/1.5B Q4_K_M, 1.5B Q4_0, 0.5B Q5_K_M, Qwen3 0.6B Q8_0, Llama 3.2
1B, Gemma 3 1B Q8_0, both qwen3moe dev models) x {short -n 48, ~600-token -n 32, AXON_REPACK=0,
AXON_SIMD=scalar}: 36/36 identical.

**Speed.** ESTIMATED roofline: a token reads 1.27 GB of experts (4 of 32, all 24 layers) + 1.33 GB of the
rest (attention Q8_0 0.68 GB, output head 0.62 GB, routers; the embedding is one row) = 2.60 GB; at bella's
~75 GB/s that is ~29 tok/s. MEASURED so far only on contended 8-E-core slots (not timing runs): Axon decode
7.8 tok/s (128 tokens, AXON_MMAP default = mapped), llama.cpp `llama-server -t 8` 5.5-6.1 tok/s
(oracle logs). The exclusive `--timing bella` A/B (`bench.sh`: Axon gen pp~500 + tg128 x3 vs `llama-bench
-p 512 -n 128 -r 3`, same threads) is job 1018-013848-7322: PENDING.

## What didn't work / notes

- Copying the model into anonymous huge pages (the dense models' default when matrices are read in
  place) was tried for gpt-oss: 12 GB of anonymous memory on a shared 30 GB box is too much (bella ran out of
  RAM once with that and a llama-server oracle side by side). Reverted: gpt-oss is always mapped, and the
  expert page tables are prefilled instead.
- `post_attention_norm.weight` was read twice (as the FFN norm and as gemma's post-norm) and the second
  read hit the released tensor: gpt-oss now reads it once, as the FFN norm.

## Stage 1 plan (GPU)

20B MXFP4 is 12.1 GB: experts 10.15 GB + 1.94 GB of the rest. A 12 GB card can't hold it all, and a
desktop keeps ~1 GB. So stage 1 is #67's split: attention, norms, sinks, router and the output head on
the GPU (1.94 GB of weights + KV: 48 KB/token at f16, 6.3 GB at 131k, or 0.8 GB at 16k), experts on the
CPU (10.15 GB mapped, 1.27 GB read per token: ESTIMATED ~45-55 tok/s at 75 GB/s minus the GPU half's
~3-4 ms/token). Pieces: an MXFP4 dequant + mmv/mmq kernel for when experts do go on a GPU (24 GB cards
hold all of it: whole-GPU path; the bytes are the file's, so upload is a copy), the sink term in
decode.cu/prefill.cu's attention (one extra (max, sum) correction per head), the window mask (gemma.cu
has it), the attention output bias, the biased router + top-4 softmax in moe.cu, swiglu_oai and expert
biases on the CPU side (already there). With 16+ GB of VRAM, hot layers' experts can live on the GPU
(llama.cpp's `--n-cpu-moe N`): the next step after the split.
