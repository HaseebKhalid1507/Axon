## 0. The thing nobody wants to hear first

**The brief's premise is wrong. The #90 gate already has a depth term.** CODE, `drafting.rs` `Fit`: the verify and
draft step costs are fitted at startup to `t(nb, Σd) = a + b·nb + c·Σd`, where Σd is the sum of the rows' positions,
over row counts {1, C, 2C, 3C, 4C, C(K+1)} × depths {512, 4096, 16384}. `round_ms` charges every verify row of a
request its own `depth + r`. That is exactly the "KV length per row" term the brief asks for; it is the same form
TurboSpec uses (§1.1). The unit test `gate_picks_r14_spec_cases` even asserts K=0 at 16k on r13's costs.

So "add depth to the cost model" is not the second attempt. The second attempt has to answer *why a gate that already
knew about depth kept drafting at 16k*. From the branch's own logs and code (ESTIMATED unless marked), the failure
has four parts, none of which is "no depth term":

1. **Unmodeled round overhead, ~1.3×.** MEASURED (run 1, d16k): rounds took 1.25–1.35× what their steps predicted.
   The 3541ea2 fix learns it online (`rcorr`, per Kmax, EMA β 1/8) **starting from 1.0, i.e. the optimistic value**,
   separately for each K. The gate therefore has to *try* K=1, learn it loses, try K=2 (rcorr[2] is still 1.0 and
   looks better), learn, try K=3, learn. Every fresh server pays that transient. The kill harness restarts the server
   per run (PR text: off / on / main interleaved per rep), so **every run is the transient**. ESTIMATED: ~50–100
   losing rounds × ~+15–25 ms on a ~28 s run at C=4 d16k ≈ 3–6 % — the size of the measured −3.2 %.
2. **Optimistic priors on α too.** `start_alpha` = the global EMA (prior 1 before any guess); a request's α moves at
   β 1/16, so a request that misses needs ~10 reached guesses before the gate stops drafting for it. At d600 that
   costs nothing (break-even α ≈ 0.35, §2.3); at 16k, where break-even is ≈ 0.7, each of those rounds is a loss.
3. **No ITL term anywhere.** Per-request pruning (`choose`: "lowest α first, drop its last guess") produces rounds
   where some rows draft and others sit at K=0 — and *every* row pays the round time. At 16k a K=1 round is ≈ 1.7×
   the plain step (§2.3). A K=0 row in such a round gets 1 token in 1.7× the time: ITL +70 %. MEASURED run 3 d16k
   ITL p99: 23.8 → 39.9 ms = **1.68×**. The p99 over 40 requests is one request; the first batch's requests live
   through the transient in (1). I can't prove which without per-request round logs (the harness doesn't emit them;
   §4 adds that), but the number is what the straggler arithmetic predicts.
4. **The α column in the kill table is a snapshot of a β-1/16 EMA, not a rate.** MEASURED run 3: d600 C=4 α 0.91 vs
   d600 C=8 α 0.63 on the *same prompts at the same depth*. Nothing about the drafter changed; the statistic is
   noise. Run 1 d16k reports kept/drafted 3022/3838 = 0.79 aggregate while the EMA read 0.23–0.90 across reps. The
   second attempt must report Σkept/Σdrafted (and per position) per cell, or we'll argue about ghosts again.

And the structural fact underneath all of it (CODE + ESTIMATED, §2.2): with today's verify, every verify row of a
slot re-reads that slot's whole KV (`Place::Rows` → `attn_blk_b`, per query; #84's `attn_blk_mq` is routed only for
*one-sequence* passes, `batch.rs` "Multi-sequence rows (serve decode) keep attn_blk_b"). At 16k the KV read is ≈ 46 %
of the plain step, so the cost ratio of a K-guess round to the plain step tends to **1 + K** as depth grows — and
E(α, K) ≤ 1 + K. **Drafting cannot win at depth with this kernel path, at any α, asymptotically.** At 16k on bella
the break-even is α > 0.71 for K=1 and the best case (α 0.9) is +16 % before overhead, i.e. a loss after it. A
perfect gate at 16k picks K=0 and delivers exactly 0 %. That is what the second attempt buys at depth: not losing.
The depth *win* (ESTIMATED +50–70 % at 16k C=4, §2.2) is stage 2 of Yoru's spec, the mq-rows verify over multi-slot
rows — the kernel already exists and is bit-identical for one sequence (#84, merged). The spec said this in October
("the mq-rows verify is the agent-depth prerequisite for C=4"); the brief has forgotten it.

Verdict on the framing: 🤡 "the gate had no depth term" — it did. 💀 the gate's priors were optimistic and its
objective ignored ITL. 🔥 the cost-model *shape* was right and the short-context wins (+24.6 %, +19.8 %) are real and
reproducible (md5 120/120).

## 1. Literature and production systems

### 1.1 TurboSpec / SmartSpec (vLLM-based; Liu, Park, Kwon, Stoica, Zhang et al.)
arXiv 2406.14066 — v1/v2 (June 2024) were titled "Optimizing Speculative Decoding for Serving Large Language Models
Using Goodput" (SmartSpec); v3 (July 2025) is "TurboSpec: Closed-loop Speculation Control System for Optimizing LLM
Serving Goodput". Same paper, same ID. Read from the v3 HTML.
- **Cost model (§4.1.3, eq. 3):** `T_fwd(M, N_context, N_batched) = α·N_context + γ·N_batched + δ`, fitted by linear
  regression from offline profiling; `α·N_context` is explicitly "KV cache loading time". **Yes, they model KV
  length**, as a sum of context tokens over the batch — identical in form to #90's `a + b·nb + c·Σd`. Draft cost
  `T_draft = s × T_fwd(draft)`.
- **Acceptance:** one *global* moving average of the acceptance rate, updated after each batch; expected length per
  request `l(α,k) = (1−α^{k+1})/(1−α)`; batch goodput `Σ_i l(α_i,k_i) / (T_draft + T_target)`.
- **K per step:** `ArgMaxGoodput` searches k ∈ 0..MAX_LEN for the whole batch (one proposed length; verification
  length may differ per request only for prompt-lookup, where some requests have no match). Not per-request K for
  draft-model speculation. Checks OOM for each k.
- **Tail latency:** none in the objective. They report per-request latency speedup; no SLO or p99 guard.
- **Overhead:** they disable the *draft model's prefill* above a learned batch-size threshold (the batch size at which
  k first hit 0), accepting that those requests never draft — the "lazy drafter feed" idea in #90's follow-ups.
- Their fig. 5: optimal k falls with batch size and with α; "propose more for small batches, less for large".

### 1.2 MagicDec (Chen, Sadhukhan, et al.; arXiv 2408.11049, v5 Apr 2025)
- Thesis: at long context the decode step is KV-bandwidth-bound, so verification of γ+1 tokens costs about the same
  as decoding 1 ("because verification and decoding share the same KV budget, their KV loading costs are
  equivalent", §3.2); hence `T_V(γ)/T_T → 1` with depth and speculation gets *better* with depth and with batch size
  beyond a "critical sequence length". Draft = the target with a sparse (StreamingLLM/SnapKV) KV so the draft's KV
  read doesn't scale.
- **The premise is a kernel property Axon's serve verify does not have.** MagicDec assumes the verify kernel reads
  the KV once for all γ+1 queries of a sequence. Axon's `Place::Rows` path reads it once *per query*, so Axon sits in
  the opposite regime: `T_V(K)/T_T → 1 + K`. That is the single most useful sentence in this document. Stage 2 (mq
  rows) is what moves Axon into MagicDec's regime; the gate alone cannot.
- Cost model: analytic (bytes of weights + KV per step / bandwidth, FLOPs / peak), used to pick the draft KV budget
  and draft model per (batch, length); they note the minimum acceptance rate for a speedup rises/falls with (B, S)
  and that "different sequences in the same batch can leverage different draft KV cache sizes".

### 1.3 EAGLE-2 (Li et al., arXiv 2406.16858)
Dynamic draft *trees*: the draft head's confidence is well calibrated, so expansion/reranking by draft probability
approximates acceptance per token. Takeaway for Axon: **the drafter's top-1 probability is a free per-token α
predictor** that needs no verified sample. For an independent 0.5B drafter the calibration is weaker than an EAGLE
head trained on target features (OPINION); measure it (§2.5, §4). llama.cpp ships the same idea as `--spec-draft-p-min`
(CODE: `common/speculative.cpp`, drafting stops when the draft's top-1 p < p_min; `n_min`/`n_max` bounds; no cost
model at all).

### 1.4 Sequoia (Chen et al., arXiv 2402.12374)
Hardware-aware: a DP picks the tree shape, and the tree *size* is chosen from a profiled verify-cost curve
`T_verify(n_tokens)` on the target hardware. Same lesson as TurboSpec: profile, don't assume. No batching, no depth.

### 1.5 SpecInfer (Miao et al., ASPLOS'24, arXiv 2305.09781)
Tree verification with a topology-aware causal mask so one pass verifies a tree; the systems point is the custom
attention kernel that shares KV across tree nodes — again, the kernel is the enabler.

### 1.6 BASS (Qian et al., arXiv 2404.15778)
Batched speculative sampling; the paper is about attention kernels for *ragged* draft lengths per sequence in one
batch and a heuristic that **adjusts the draft length per step from the accepted length** (shrink on low acceptance,
grow on high). Confirms per-sequence ragged K is feasible when the kernel handles it, and that a cheap
accepted-length feedback rule is what practitioners actually ship.

### 1.7 SpecDec++ (Huang et al., COLM 2025, arXiv 2405.19715)
Candidate length as an MDP; the optimal policy is a *threshold*: stop drafting when P(at least one rejection so far)
exceeds a threshold. Uses a trained acceptance head on the draft. Axon's analogue without training: stop at the
first guess whose drafter top-1 p is below a depth-dependent threshold (§2.4).

### 1.8 SLO-aware variants
AdaSpec (arXiv 2503.05096; "SLO-aware ... adaptive speculative decoding", code on GitHub) and AdaServe
(arXiv 2501.12162; per-request SLO-customised speculation trees, "speculate–select–verify"). Both put a latency
constraint into the K choice; AdaServe does it per request. Neither models KV length explicitly in the abstract; I did
not read their bodies — cited for the *constraint* idea only.

### 1.9 What production schedulers actually do today (CODE, upstream main as of 2026-10-24)
- **vLLM** (`vllm/config/speculative.py`): `num_speculative_tokens_per_batch_size: list[(range_start, range_end,
  k)]` — a **static batch-size → K schedule**. `enable_adaptive_verification` (per-request confidence) exists only
  for `method="dspark"`. No goodput estimator, no KV-length term, no latency guard in mainline; SmartSpec's "DSD"
  lived in a fork. The old V0 `speculative_disable_by_batch_size` is gone.
- **SGLang** (docs "Adaptive Speculative Decoding"): EAGLE/EAGLE3 with topk 1 only. EMA (α 0.2) of the batch-average
  accepted length, **independent trackers per batch-size range**, candidate step tiers per range (default: BS 8–31
  ∈ {1,3}, BS ≥ 32 locked at 1), `warmup_batches` 10, `update_interval` 5, down/up hysteresis, optional "ceiling"
  capping steps by observed draft quality; each tier owns pre-captured CUDA graphs so switching is a pointer swap.
  **No cost model, no depth, one K for the whole batch, no tail guard** — but hysteresis, warm-up and per-regime
  tracking are exactly the things #90 lacked.
- **llama.cpp server**: per-slot drafting, `p_min` confidence stop, `n_min`/`n_max`; speculative batch size limited
  by `n_batch`/`n_parallel` (`common_speculative_get_output_limits`). No cost model.

### 1.10 What this says for Axon
Everyone with a cost model uses #90's linear form, and everyone fits it from profiling. Nobody in production gates
per request with a latency constraint, and nobody has solved "verify re-reads the KV per row" with a gate — they
solved it with a kernel (MagicDec/SpecInfer/BASS) or avoided depth. The novel parts of v2 are (a) the ITL constraint,
(b) pessimistic priors with measured round overhead, (c) per-depth-regime tracking à la SGLang. None is research
risk; all are engineering.

## 2. Design: the depth-aware gate, second attempt

### 2.1 Measured anchors (bella, 7B Q4_K_M + 0.5B Q4_K_M, C=4)
MEASURED plain step time from run 3's off rows: agg tok/s → ms/step at C=4: d600 328.9 → **12.2 ms**; d4k 276.9 →
**14.4 ms**; d16k 185.0 → **21.6 ms**. ESTIMATED slope: (14.4−12.2)/(4·3.4k) = 1.6e-4 and (21.6−14.4)/(4·12k) =
1.5e-4 ms per (row·position): **c ≈ 1.5e-4 ms/row/pos**, consistent across the two intervals, so linear-in-Σd is the
right shape (the test comment's bella fit has c = 1.3e-4, b = 0.34, a = 11.7; the drafter 2e-5 / 0.02 / 2.5). Sanity:
7B Qwen2.5 KV ≈ 56 KiB/position (spec §3.7); 150 ns per position per row ≈ 380 GB/s ≈ 38 % of the 4090's bandwidth
for the per-query attention path — not great, but that's #50's territory, not this one's.

### 2.2 Cost model (what changes from #90)
Keep the form; change what is tabulated vs fitted, and add the terms that were missing.

```
T_plain(n, D)        = T0_v[n][0]            + c_v · D                      D = Σ_i d_i (one row per request)
T_verify(n, K, D)    = T0_v[n][K]            + c_v · Σ_i Σ_{r=0..K} (d_i + r)
T_draft_j(n_j, D_j)  = T0_d[n_j]             + c_d · D_j                    j-th draft step, n_j rows still guessing
T_round(n, K, D)     = Σ_j T_draft_j + T_verify + h · (K + 1) + S(gap)
```
- **`T0_v[n][K]` is a table, not a plane.** nb = n·(K+1) with uniform K (§2.3) takes at most 4 values per n; C ≤ 8
  and K ≤ 3 is 32 shapes. MEASURED (#81, c-curve): the 7B step jumps 8.6 → 13.4 ms between nb 16 and nb 24 (gemvm →
  gemm2 tiles) and is flat to 64. A plane in nb through that cliff is wrong on both sides; #90's per-nb `vcorr` EMA
  papered over it. Tabulate at two depths (512 and the slot context) and fit only `c_v` across depths — the one
  dimension where physics says linear.
- **`h`: host + sync overhead per step** (a device→host pick copy and a sync per draft step and per verify, the row
  building, the walk). Measured at calibration as (round wall − Σ step kernel time)/(K+1) by running *whole rounds*
  with garbage tokens, not just steps. ESTIMATED order 0.2–0.5 ms per step; unknown — the 1.3× says something costs
  ~10 ms per round at d16k and ~8 ms at d600 (§2.6), and until it's profiled the gate is guessing.
- **`S(gap)`: the switching cost.** When a request drafts after `gap` plain rounds, its drafter slot is `gap` tokens
  behind; ≤ `STEP_CATCH_UP` = 2 rides as extra rows in the first draft step, more is a `feed_slot` prefill (CODE,
  `engine.rs` `round`). `S(gap) = T0_d[1] + b_d·gap + c_d·d` per such request. #90 attributed this to `rcorr[K]`, so
  a gate hovering at the margin taught itself that K itself was expensive. Model it explicitly and *amortise* it:
  a drafted round after a gap is charged `S/H` with horizon H = 16 rounds, and the gate requires the expected gain
  over H rounds to exceed S (a hysteresis that falls out of the model rather than a magic threshold).
- **Online correction:** one EMA per *shape* (n, K) of measured/predicted round time, β 1/8, **initialised from the
  startup round calibration, not from 1.0**. Shapes never run keep the calibrated value. A separate EMA for
  `T_plain` per n (the plain step is measured every round anyway).
- **Persist the calibration** (`--draft-calib-file`, JSON keyed by the identity tuple + GPU name): a server that
  restarts does not relearn. Cheap, and it removes the per-run transient from every future benchmark.

### 2.3 Decision rule
Per step, with n running greedy requests at depths d_i, α estimates (§2.5) and caps (sampled → 0; near `max_tokens`;
past the drafter's ctx):

```
for K in 0..=3:
    K_i = min(K, cap_i)                               # uniform K; cap only shortens
    T   = T_round(n, K, D)  (with S amortised if the previous round had K=0)
    E_i = 1 + Σ_{j=1..K_i} Π_{m≤j} p_i,m               # positional acceptance, §2.5; geometric α_i^j if unknown
    G   = Σ_i E_i / T
    feasible iff for every row i:  T / E_i ≤ (1 + δ) · T_plain      # the ITL guard, δ = 0.10
    (a row with K_i = 0 has E_i = 1, so feasibility there means T ≤ 1.1·T_plain)
choose the feasible K with the largest G; K=0 is always feasible (G = n / T_plain).
```
Why **uniform K** instead of #90's per-request pruning: the ITL guard makes mixed rounds infeasible whenever the
round is more than 10 % longer than the plain step, which at ≥ 4k is always. Per-request K would only matter in the
region where the round is nearly free, i.e. d600 at C ≤ 4 — and there K=3 for everyone is right anyway (MEASURED
+24.6 %). Uniform K also collapses the step shapes to 4 per n (graphs, tables, tests). Keep the per-request *cap*.

Why **δ = 0.10, not 0.15**: the kill rule is on p99 over requests of mean ITL; δ bounds every round's expected ITL,
and the realised one is worse for an unlucky request (its guesses missed). 5 points of margin is OPINION; §4 measures
whether it holds.

Break-even and the guard at C=4 on bella (ESTIMATED with §2.1's anchors, extra verify row = 0.34 + c·d, drafter step
= 2.5 + 0.02·4 + 2e-5·4·d, no overhead):

| depth | T_plain | ρ(K=1) = T_round/T_plain | α needed, K=1 | ρ(K=3) | α needed, K=3 | ITL guard admits K=3 iff |
|---|---|---|---|---|---|---|
| d600 | 12.2 | 1.35 | > 0.35 | 2.07 | > 0.50 | E_i ≥ 1.88 → α_i ≳ 0.50 |
| d4k | 14.4 | 1.47 | > 0.47 | 2.40 | > 0.62 | E_i ≥ 2.18 → α_i ≳ 0.60 |
| d16k | 21.6 | 1.71 | > 0.71 | 3.12 | > 0.85 | E_i ≥ 2.84 → α_i ≳ 0.78 |

Read it: at 16k with an aggregate α of 0.79 (run 1's kept/drafted) K=1 is +4 % *before* overhead → off after it,
and K=3 scrapes past the guard but loses on goodput (E 2.9 vs ρ 3.12); at d600 the same α is +30 % at K=1 and K=3
is admitted. The guard is what protects the *low-α rows* in a batch (a fresh request's LCB, a prose request among
code ones); the goodput is what turns 16k off. Both are needed: run 3 had the second and not the first.
Note the guard also bites at d4k C=8 (MEASURED run 3 ITL p99 +14.3 %, a hair under the bar): the uniform-K rule with
δ = 0.10 would have chosen K=1 there, which the gate's own arithmetic (spec §1: C=8 d4k K=1 +15 % vs K=3 +5 %) says
is also the better goodput. Good sign when the constraint and the objective agree.

### 2.4 Drafter-side early stop (optional, cheap, lossless)
Return the drafter's top-1 probability with its pick (`RowHead::Argmax` → a second f32 per row; drafter only, the
main model's rows are untouched). Stop a request's guesses at the first guess with p < p_min(d), where p_min is the
positional break-even from the table above (≈ 0.35 at d600, ≈ 0.7 at 16k). This is llama.cpp's `p_min` and
SpecDec++'s threshold policy with the threshold set by the cost model instead of a flag. It shortens verify rows for
requests that are about to miss *this* round rather than on average. It changes K_i per request, so the shape table
needs nb ∈ n..n(K+1) again (the graphs are cheap; the table can interpolate between the uniform points). OPINION:
build §2.2–2.3 first, measure, then decide whether this is worth the shape count.

### 2.5 α estimation
- **Per request: a Beta posterior, decided on its lower bound.** Prior `Beta(n0·ᾱ, n0·(1−ᾱ))` with ᾱ the server's
  rate for the request's depth bucket and n0 = 8 pseudo-observations; each reached guess adds 1 to kept or missed;
  the gate uses `α_lcb = mean − 1·sd`. A fresh request at 16k with ᾱ = 0.79 has α_lcb ≈ 0.65 → the K=1 break-even
  (0.71) is not met → no drafting until evidence arrives; at d600 (break-even 0.35) the same prior drafts at once.
  That is the whole point: uncertainty should cost drafting exactly where the margin is thin. #90's β-1/16 EMA from a
  point prior has no notion of confidence.
- **Positional acceptance, not one α.** Keep p_1, p_2, p_3 (P(guess j kept | guesses < j kept)) per depth bucket
  server-wide, as llama.cpp's `n_accepted_per_pos`. E(K) = 1 + p_1 + p_1p_2 + p_1p_2p_3. The geometric model
  overstates E at K=3 when p falls with position (OPINION: it does for a 0.5B drafter). Per request, a single α
  posterior scales the bucket's positional curve.
- **Server-wide, per depth bucket** {< 2k, 2k–8k, > 8k}, exponential forgetting with an effective window of ~256
  guesses (β 1/256): slow enough not to bounce by 0.3 between two runs of the same prompts, fast enough to follow a
  workload shift within a few hundred tokens (TurboSpec's distribution-shift test, §1.1). SGLang's per-batch-size
  slots are the same idea on a different axis; depth is the axis that matters here.
- **Report** Σkept/Σdrafted per cell and per position in the harness; drop the EMA snapshot from the tables.

### 2.6 Probing without hurting ITL
#90's probe (every fresh request guesses once, alone) is one Bernoulli sample bought with a round that is +30 %
longer for everybody at 16k. Replace it with:
1. **Free probes first.** When the gate drafts anyway (any depth where K ≥ 1 is feasible), every request in the
   round is observed; no probing needed.
2. **Guarded probes.** When the gate is off, a probe round is allowed only if the ITL guard admits it: `T_probe ≤
   1.1·T_plain`. At 16k a K=1 probe for one row costs one drafter step (≈ 3.9 ms) + one verify row (≈ 2.8 ms) on a
   21.6 ms step = +31 % → **not admitted**. At d600 it's +25 % → not admitted either, but at d600 the gate is on, so
   it doesn't matter. In practice probes happen only in the band where drafting is marginal — which is where
   information is worth the most.
3. **Rate-limit** probes to one per request per 64 rounds and spend them on the request with the widest posterior
   (largest sd), K=1 only. The drafter's catch-up for a probing request is `S(gap)` — charge it.
4. **Drafter confidence as a free signal** (§2.4) once it's wired: a request whose drafter top-1 p averages 0.9 at
   16k is worth a probe; one at 0.4 is not.
5. **Startup calibration of rounds** (§2.2) makes the rcorr learning transient disappear; the α prior comes from
   the depth bucket; nothing needs to be "tried" to be known.

### 2.7 Where the 1.3× goes — measure before designing further
ESTIMATED from run 3: at d600 C=4, K=3, α ≈ 0.9 → E ≈ 3.44; predicted round ≈ 12.2 × 2.07 = 25.2 ms; measured
agg +24.6 % implies a round of ≈ 12.2 × 3.44 / 1.246 ≈ 33.7 ms → **1.34× at d600 too**. So ~8–10 ms per round
is unaccounted for at every depth — the size of a whole 7B step. Candidates, in my order (OPINION): (a) K+1
device→host syncs per round (each draft step returns picks before the next can be built); (b) catch-up `feed_slot`s
after K=0 stretches; (c) catch-up rows changing the drafter's nb so its graph key misses (keys are `(nb, ng, ns)`,
MAX_GRAPHS 64 — probably fine, but check the capture counter); (d) the walk + `emit` per token under the engine lock.
First build-day task: an nsys trace of 20 rounds at d600 and d16k with per-step timestamps; print round − Σkernels.
If (a) dominates, batching the K draft steps into one graph with device-side argmax feeding the next row (the
drafter's picks never need the host until verify) removes K syncs; that is a drafter-only change with no bits risk.

## 3. Exactness
- **Unchanged by construction.** The gate chooses *whether and how many* guess rows to verify. Each verify row's
  pick is `verify_argmax`'s bit for bit (CODE: the pool contract, `pool_rows_of_many_slots_match_verify`), and the
  walk is `generate`'s (`engine.rs` `round`: stop ids → push → emit → n_gen, taking row j only if row j−1's pick
  equalled guess j). A rejected guess's KV rows are overwritten by the next round and never read. So K=0, K=1 or
  K=3, probe or not, the emitted bytes equal the plain server's. MEASURED: 120/120 md5 identical off / on / main in
  run 1 and run 3; `serve_batched_draft_matches_plain` covers stop strings, mid-round caps, a cancelled stream and
  sampled rows mixed in.
- **New code in v2 that touches bits: none.** The cost table, the Beta posterior, the ITL guard, the switching cost
  and persistence are host arithmetic. §2.4's drafter top-1 probability is a second output of the *drafter's* head;
  the drafter's outputs can only change which guesses are offered, never what is emitted.
- **Two things to re-check on the rebase**, because main moved (paged KV #64/#68/#71 and #84 merged after the
  branch): (i) startup calibration steps write garbage rows into empty slots and, under pages, `step` *reserves*

## 6. Top risks
1. **The 1.3× is not where I think it is** (OPINION on the causes; MEASURED on the size). If it's the drafter steps'
   syncs it's fixable in half a day; if it's something structural in `Batch::round` under the engine lock, the
   short-context wins shrink too and the +10 % bar at d4k C=4 gets tight (run 3 had +19.8 % with the overhead in).
2. **α really is low at depth.** If the 0.5B drafter's acceptance on real 16k agent histories is ~0.5 (run 3's
   snapshot said 0.54; run 1's aggregate said 0.79 on synthetic padding), then even stage 2's verify gives
   E(0.5, 3) = 1.875 and the depth win is ~+30 %, not +50–70 %. The harness pads with a synthetic history; a cell
   with a *real* 16k session (one of the agent transcripts) is the honest measurement and should be added when one
   exists.
3. **The ITL guard over-constrains C=8.** At d4k C=8, ρ(K=1) with 8 extra rows and the gemvm→gemm2 cliff (nb 16) may
   exceed 1.1 so the guard disables drafting where run 3 found +1.4 %. That trades a 1 % win for a 14 % ITL
   improvement; the spec's bar for C=8 is "nothing lost", so it passes — but if the owner wants the C=8 win, δ has
   to be a knob (`--draft-itl-slack`), defaulting to 0.10.
4. **Rebase cost.** The branch predates paged KV and #84; `slots.rs` moved 150 lines for `pool_rows`, `serve.rs` 120.
   Budgeted at 0.5 day; could be 1.5 if `new_pool_rows` and the paged `reserve` path fight.
5. **Measuring on bella only.** A 4090's bandwidth/compute ratio sets c and the cliff at nb 16; the H100 board
   (10-19) shows Axon decode-bound differently at C ≥ 8. The gate is self-calibrating, so it should transfer, but
   nothing in §4 proves it. Add one H100 d4k C=4/8 cell when a pod is up anyway; don't block on it.
6. **Shipping the gate without stage 2 and calling it "speculative decoding for agents".** It isn't. It's a short-
   context feature with a depth-safe off switch. Say so in the README row, or someone will run a 20k session and
   file "speculation does nothing".
